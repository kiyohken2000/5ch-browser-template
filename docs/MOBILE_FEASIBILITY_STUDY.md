## 2. 不変条件（機能より優先する制約）

既存のモバイル専ブラ 2 大手は、小規模な現役勢に評価で大きく負けている（§15-2）。

| アプリ | 評価 | レビュー数 | 規模 |
|---|---|---|---|
| chMate (Android) | **1.8** | 23,300 | 100 万+ DL |
| twinkle (iOS) | **1.68** | 5,101 | — |
| Geschar (iOS) | **4.42** | 2,614 | — |
| したらばStorm (Android) | **4.3** | 1,280 | 1 万+ DL |

chMate のレビューに原因が具体的に書かれている（§15-2 に引用）。**そこから導いた 5 条件を、M1 以前の前提とする。**

| # | 条件 | 実装上の意味 |
|---|---|---|
| **1** | **広告を入れない。アプリ内課金を入れない** | 収益化が必要なら寄付（Ember は既に `BUY_ME_A_COFFEE_URL` を持つ）。chMate の不満の 1 位は「広告の挙動によるフリーズ」で、課金していた中核ユーザーが離反し返金告知まで出ている。**2026-11-04 に `react-native-purchases` が依存に入ったが、まだ呼んでいないのでこの条件は有効。採否は #14** |
| **2** | **NG をすべての描画経路で効かせる** | 本文リスト / 参照ポップアップ / ID シート / 被参照一覧 / 検索結果。これらは別経路なので適用漏れが起きやすい。「NG レスがアンカで見えてしまった」が実際の不満として挙がっている |
| **3** | **ソートと既読位置を勝手に変えない** | 更新してもソート順を維持し、既読位置を失わない。「未読スレのソートが勝手に弄られる」が不満として挙がっている |
| **4** | **固まらない** | AI 推論・画像デコード・AA 判定・大量レスの描画を UI スレッドから外す。Skia / reanimated / worklets が揃っているので手段はある |
| **5** | **既読とお気に入りを壊さない** | 書き込みは一時ファイル + rename。デスクトップ版は `fs::write` が先に 0 バイトへ切り詰めるために既読が丸ごと消える事故を経験しており、同じ対策が入っている |

## 3. 技術スタック

### 3-1. ルート選択

**React Native / Expo を採用する。**

| 案 | 評価 |
|---|---|
| **React Native / Expo** | **採用。** ユーザーの主戦場であり、同種アプリ（BakuSoku / スキキラ / kenmo reader）と AI 基盤（FeedOwn）の実績がある |
| Tauri v2 のモバイルターゲット | **不採用。** Rust 5 crate と React を再利用できる見かけの魅力があるが、`core-ai/Cargo.toml` が `cfg(not(target_os = "macos"))` → vulkan を選ぶため iOS で壊れる。`llama-cpp-2` のモバイル向けクロスコンパイルは整備されておらず、UI も結局書き直し。ツールチェーンとストア配布の実績も薄い |

Tauri を選ぶ唯一の利点は WebView なので `backdrop-filter` / `InputEvent.inputType` / `getCaretClientPoint()` がそのまま動き、**ガラスとコンボ演出を 1 ピクセルも変えずに保存できる**こと。しかし演出の一点のためにツールチェーンのリスクを負うのは割に合わない（代替は §9-3 / §9-4）。

**反証候補とその決着（2026-11-04）:** 同種の専ブラ `bbs-browser` が、まさに **Tauri v2 の同一ソースからスマホ版を作る**と宣言している（§15-6）。`docs/mobile.md` に「PC 版と同じソース(Tauri v2)から作る。画面と操作だけを、スマホのときに変える」と明記されている。ただし **Android 版は「準備中」で APK はまだ 1 つも出ていない**ので、動く証拠にはなっていない。

そして**同日、iOS / Android の同時ストアリリースが決定したことで、この反証候補は閉じた**（§13-4）。`core-ai/Cargo.toml` が `cfg(not(target_os = "macos"))` で vulkan を選ぶため iOS で壊れる以上、**iOS をやるなら Tauri は選べない。** 向こうが動く APK を出しても判断は変わらないので、再評価のトリガー自体が消えた。Ember が React Native を選ぶ理由（ローカル LLM の既存資産 §5-2、ネイティブ通知と背景実行 §9-8、ユーザーの主戦場）も何も変わっていない。**React Native 採用は確定。**

根拠は 4 つ。雛形である **FeedOwn は `axios` を 1 ファイルも import しておらず**（`apps/mobile/src/` 全検索）、実際に使っているのは `fetch` だけ（`utils/api.js` / `scenes/read/Read.js` / `utils/supabase.js`）。`package.json` の `axios ^0.21.2` はボイラープレートから引き継いだ死んだ依存で、2021 年系かつ CVE がある。タイムアウトとキャンセルは `AbortController` で足りる。そして新規 npm 依存を増やさない（`CLAUDE.md` の禁止事項）。

**ただし条件付き。** Shift_JIS のバイト列を `fetch` の `arrayBuffer()` で Android / Hermes から素直に取れるかは **M0 で実測する**（§12-0）。ここが通らなければ最新系列の axios に落ちる、という形で第一候補を固定した判断。

### 3-5. 設計方針の分岐点: Redux

ボイラープレートは Redux Toolkit 前提。一方 **Ember デスクトップ版は `CLAUDE.md` に「Redux, Context Provider は不使用」と明記し `useState` のみで通している。**

画面が分かれる RN では Redux の方が自然なので悪い選択ではないが、**`App.tsx` のロジックを素直に写せない。**

**決定（2026-11-04）: Redux Toolkit を使う。** ボイラープレート / FeedOwn / BakuSoku / sukikira の 4 本すべてが `@reduxjs/toolkit` を入れており、雛形から外す方がコストが高い。デスクトップ版の「Redux 不使用」は `App.tsx` 単一モノリス前提の規約で、画面が 14 本に分かれるモバイルには持ち込まない（§4-3）。**系列は 2.x** — 4 本とも `^1.5.1` だが新規なので最新系列に上げる。

### 3-6. 最小 OS とアプリサイズの見込み

参考値（§15-1）: Geschar は 38MB / minOS 16.4、twinkle は 26MB / minOS 12。

Ember モバイル版は Skia + llama.rn を含むため**基本サイズは 50〜80MB 程度になる見込み（推測）**。AI モデルは同梱せずダウンロードするのでバンドルには乗らない。最小 OS は Expo 58 の要件に従う。**iOS は 17.0。** FeedOwn の `app.json` が `deploymentTarget: "17.0"` で、Expo 58 + llama.rn の実測値。**2026-11-04 に `expo-build-properties` で `app.json` に書き込んで実際に効かせた**（`npx expo config --type prebuild` で確認済み）。

### 3-7. リポジトリ配置（決定）

**Ember のモノレポに `apps/mobile` として置く。**

| 理由 | |
|---|---|
| 既存の規約に乗る | 既に `apps/desktop` と `apps/landing` がある |
| **プロトコル実装を共有できる** | `core-parse` の TS 移植（§12-0）を 1 箇所に置ける。ここが最も高価な資産 |
| ドキュメントが一箇所にまとまる | 本文書と `docs/DEVELOPER_GUIDE.md` が同じリポジトリにある |
| 前例がある | FeedOwn も `apps/mobile` + `apps/web` のモノレポ構成 |

**注意点:**

- **`scripts/release.sh` は固定ホワイトリスト方式**なので、`apps/mobile/` のファイルはデスクトップ版のリリースコミットに入らない。モバイルは EAS で独立してリリースする（§17）。**デスクトップのリリース手順に干渉しない**
- **CI は別ワークフローを足す。** 既存の cargo / tsc / Playwright のワークフローは触らない（§16）
- `apps/mobile/` は自前の `package.json` を持ち、`apps/desktop/` とは独立して依存を管理する
- **共有コードの切り出しは急がない。** `core-parse` の TS 版は M1 では `apps/mobile/` 内に直接置き、2 つ目の利用者（デスクトップ側の逆輸入など）が出てから `packages/` へ切り出す

## 6. アプリの性格

### 6-1. 何であって、何でないか

デスクトップ版の Ember は**作業台**である。タブを 20 本開き、3 ペインで俯瞰し、全タブ更新で一斉に回す並列監視の道具。

**スマホに縮めても意味がない。画面が 1 枚しかないので並列性が死ぬ。**

モバイル版は**通知駆動の実況・追跡アプリ**。開きっぱなしで並べるのではなく、閉じている間に動きがあったものが上がってくる。**入口はタブのクリックではなく、通知と監視リスト。**

### 6-2. 対応概念の変換

| デスクトップ | モバイル |
|---|---|
| スレタブバー | **監視リスト + 新着バッジ**。タブを持たない |
| 3 ペイン + スプリッタ | 板 → スレ一覧 → レス のスタック遷移 |
| 全タブ更新ボタン | ホームの Pull to refresh |
| マウスホバーでポップアップ | **タップでポップアップ**（`touchMode` の既存分岐が本番になる） |
| ID クリックメニュー | 長押しメニュー |
| マウスジェスチャ（右ドラッグ） | スワイプ（§9-1。縦スワイプの衝突に注意） |
| キーボードショートカット 22 種 | 廃止 |
| `autoRefresh` | Pull to refresh + 実況モード |
| ガラス効果 / ウィンドウ管理 / 自動アップデータ | §9-3 / 廃止 / ストア + `expo-updates` |

### 6-3. モバイルで増える価値

- **PC が落ちていても新着を追える**（デスクトップの Discord 通知は PC 稼働が前提、§9-8）
- **通知をタップしてそのままスレへ入れる**
- **オフライン閲覧**（通勤前に取得して地下鉄で読む）
- **共有シート連携**（ブラウザの 5ch URL → 共有 → Ember で開く / スレを送る）
- **カメラロール・カメラからの画像投稿**
- **実況モード**（自動追従・省電力）

**注意: この 6 項目はすべてモバイル単体の価値で、デスクトップ版との相乗効果はここに含まれない。** 相乗効果の評価は §14 の「#1 について」。

### 6-4. 設計原則

1. **1 画面 1 目的。** 3 ペインを 3 画面に分解し、同時に見せない
2. **ホバーの代替は長押し、クリックの代替はタップ**
3. **入口は通知と監視リスト**
4. **読む機能を最優先。** 設定は深い階層でよい。デスクトップは設定 6 タブ 67 項目あるが、モバイルで全部は要らない（§8-14）

#### 表示密度（M4）

`bbs-browser`（§15-6）は「レスの見た目」を **カード / Discord 風 / LINE 風 / 専ブラ風 / まとめ風**の 5 モードで持っている。**モードを 5 つ増やすのではなく、密度の 1 軸だけを採る。**

| 設定値 | 中身 |
|---|---|
| **ゆったり**（既定） | カード。枠線と余白でレスを区切る |
| **つめる** | 枠線・影・カード余白を外してフラットに並べ、左に **ID から生成した丸アイコン**を置く |

**なぜ密度なのか:** スマホは縦がすべてで、1 レスあたりのクロームを削ることがそのまま可読量になる。Discord 風の見た目の価値はここにある。

**本体は並びではなく ID アイコン:**

- スマホでは ID の 8 文字は小さすぎて読めない。アイコンは「さっきと同じ人だ」を**読まずに**判別できる唯一の手段になる
- 生成元は ID 文字列のハッシュ。**本文中 ID の着色（§8-4 の表）と同じ色を使う**ので、色の決め方を一本化する
- **カードのままアイコンだけ足しても価値の 8 割は取れる。** 「つめる」が見送りになってもアイコンは単体で入れられる
- **意味の限定を明示する:** ID は日付で変わる。アイコンは**そのスレ内で同じ人**の印でしかなく、日をまたいだ同一性は示さない。UI にこの説明を置く

**ハッシュ方式（決定、2026-11-04）:**

| | |
|---|---|
| 関数 | **FNV-1a 32bit。** TS と Rust で同一結果を 10 行で書けるので、デスクトップ版への逆輸入がそのまま効く。暗号ハッシュは使わない（速度と、両言語での実装一致を優先） |
| 色 | `hash % 20` → 既存の `ID_COLORS` / `ID_COLORS_DARK`（各 20 色）をそのまま使う。**色そのものではなく添字を覚えてライト / ダーク間で色相を保つ現行設計は活かす** |
| アイコン | **同じハッシュの別のビット領域**から形状と配置を引く。色だけでは 20 通りなので同一スレ内の衝突が必ず起きる。形状を掛けて見分けを増やす |

**この決定はデスクトップ版の現状も直す。** `App.tsx:2341-2349` の `getIdColor()` は `idColorMap.size % ID_COLORS.length`、つまり **出現順**で添字を配り、`App.tsx:6062` でスレ切替ごとに `clear()` している。そのため「同じ ID は常に同じ色」が構造的に保証されていない — **NG を増減すると、消えたレスの ID がマップに入らず以降の添字がずれる。** ハッシュなら ID だけで決まり、`idColorMap` と `clear()` が不要になる（状態が消える）。**デスクトップ版への適用は §14-8 と同じく別途承認が必要。**

**制約（必須）:**

- **AA と判定したレスは、密度設定に関わらず常に全幅カードで描く**（§9-2）。左のアイコン溝を取られると AA は読めなくなる
- 密度は**描画経路を増やす**。不変条件（§2）の「NG はあらゆる描画経路で効く」は密度ごとに成り立たせる。毎リリース検査も密度ごとに回す（§16-3）

## 9. 横断する仕様

### 9-1. ジェスチャ

Geschar は「ジェスチャ操作を特色とした」の一行だけで評価 4.42（§15-3）。**ジェスチャを後付けの便利機能ではなく操作体系の中心に置く。**

#### デスクトップの既存資産

`App.tsx:590-664` に完成した仕組みがある。**17 アクション × 12 パターン**、ユーザーが割り当て変更可。

既定: `←`=前のタブ / `→`=次のタブ / `↓`=スレッド更新 / `↑`=先頭へ / `↑↓`=末尾へ / `↓→`=タブを閉じる / `↓←`=スレッド一覧を更新

#### 問題 1: 17 アクションのうち 7 個がタブ操作

| デスクトップのアクション | モバイル |
|---|---|
| `prevTab` / `nextTab` | **前のスレ / 次のスレ**（監視リストの順）に読み替え |
| `closeTab` | **監視リストから外す**に読み替え |
| `closeOtherTabs` / `closeTabsRight` / `closeTabsLeft` / `closeAllTabs` | **落とす**（「右側」「左側」の概念が無い） |
| `reloadThread` / `reloadThreadList` / `reloadAllTabs` | **Pull to refresh に昇格。** 各画面の標準動作にするのでジェスチャから外す |
| `scrollTop` / `scrollBottom` | 残す。長いスレで価値が高い |
| `toggleThumbMask` | 残す。**公共の場で即マスクできる実用性はデスクトップより高い** |
| `toggleDark` | 残す |
| `purgeCache` | 残す（長押しメニュー側でもよい） |
| `openSettings` | 落とす（ボトムタブにある） |

#### 問題 2: 縦スワイプは本文スクロールと衝突する

デスクトップのジェスチャは**マウスの右ドラッグ**なのでスクロールと共存できた。モバイルでは **1 本指の縦スワイプはスクロールそのもの**なので、既定 7 割当のうち 5 つ（`↑` `↓` `↑↓` `↓→` `↓←`）がそのままでは成立しない。

#### モバイル用のジェスチャ語彙

| ジェスチャ | 割り当て | 衝突の注意 |
|---|---|---|
| リスト最上部からの下スワイプ | 更新 | OS 標準の pull to refresh に一致 |
| 本文領域の左右スワイプ | 前のスレ / 次のスレ | **iOS の画面左端スワイプ（戻る）を避ける。左端 50pt は反応させない**（スタックの戻るジェスチャの既定幅に合わせた。当初は 20pt） |
| **2 本指の上スワイプ** | 先頭へ | 1 本指のスクロールと分離できる |
| **2 本指の下スワイプ** | 末尾へ | 同上 |
| 画面上端（ステータスバー）タップ | 先頭へ | iOS 標準の挙動に乗る |
| **長押し** | レスメニュー | |
| ピンチ | 文字サイズ / AA の縮尺 | |
| 2 本指タップ | サムネマスク切替 | 要検討 |

**割り当て変更 UI はデスクトップ版と同じく用意する。** `GESTURE_PATTERNS` / `GESTURE_ACTIONS` の構造をそのまま使い、パターン定義だけ差し替える。

### 9-2. AA（アスキーアート）表示 — 新規実装

**Ember には AA 向けの処理が一切ない**（`aa-` / `aaMode` / `AAフォント` の grep が全 0 件）。twinkle が説明文の 2 番目に「アスキーアートを自動で判別し、画面にフィットさせて表示」と書いている（§15-4）のは、**モバイルでは必須級**という意味。

#### なぜモバイルで必須か

- 5ch は AA 文化を持つ。モナー系の AA、表組み、罫線素片を使ったレスが普通に流れる
- デスクトップは横幅が十分あり等幅フォントも効くので、何もしなくても大きく崩れない
- **スマホの狭い画面では折り返しが入り、AA は完全に読めなくなる**
- **さらに「長文の折りたたみ」が AA を確実に引っかける**（行数で判定するため）

#### 検出（ヒューリスティクス）

レス単位ではなく**連続する行のブロック単位**で判定する。

| 指標 | 閾値案 |
|---|---|
| 連続行数 | 3 行以上 |
| 全角スペースの連続 | 1 行に 2 個以上連続する箇所がある |
| 記号・罫線素片の比率 | 行の文字数に対して 30% 以上（`─│┌┐└┘├┤┬┴┼` `＼／∧＿￣` 等） |
| 行長のばらつき | 小さい（AA は行長が揃う傾向） |

**誤検出の方向を決めておく:** 表組みや区切り線を AA と誤判定しても害は小さい（等幅で出るだけ）。逆に AA を見逃すと壊れて表示される。**再現率（取りこぼさないこと）を優先する。**

#### 表示

| 方式 | 採否 |
|---|---|
| **横スクロール** | **既定。** 文字サイズを維持したまま読める |
| 幅に合わせて縮小 | 既定にしない。横に長い AA だと文字が小さくなりすぎる |
| タップで全画面表示（ピンチズーム可） | **横スクロールと併用して用意する** |

**フォントの限界（正直に書いておく）:** 5ch の AA は **MS Pゴシック前提**のものが多い。モバイルに MS Pゴシックは無いので等幅フォント（ヒラギノ角ゴ / Noto Sans Mono CJK 等）で代替し、**一部の AA は完全には再現できない。** 専ブラ共通の制約で解消はできない。目標は「崩れの最小化」。

#### 折りたたみとの相互作用（必須）

**AA と判定したブロックは折りたたみの対象から外す。** これを入れないと AA が「…続きを読む」で切られて壊れる。

#### 表示密度との相互作用（必須）

**AA を含むレスは、表示密度が「つめる」でも常に全幅カードで描く**（§8-4）。アイコン溝の分だけ横幅を失うと AA は崩れる。吹き出し型の表示を採らない理由も根は同じ（§15-5）。

#### 逆輸入

この機能はデスクトップ版にも無い。**モバイルで作ってからデスクトップへ戻すのが筋**（検出ロジックは TypeScript なので共有できる）。ただしデスクトップへの適用は別途承認が必要（§14-8）。

### 9-3. ガラス効果

**残せる。iOS では向上する。**

WebView の `backdrop-filter` はブラウザがソフトウェア寄りで合成するため重い。iOS の `expo-blur`（ネイティブ `UIVisualEffectView`）は OS が GPU で処理する本物のすりガラスで、**デスクトップ版より速くて綺麗になる。** CSS 98 宣言 / 関連 423 箇所は作り直しだが、**作り直した方が品質が上がる。**

**弱点 2 つ:**

1. **Android が劣る。** リアルタイムブラーはコストが高く `expo-blur` の Android 実装は iOS ほど安定しない。**ブラー無しの半透明フォールバックを最初から設計に入れる。** 後付けだと破綻する
2. **屋外の可読性。** スマホは直射日光下で使う。**ガラスは本文に掛けない。** バーやパネルなどのクロームに限定し、レス本文は不透明な面に置く。デスクトップ版より厳しく線を引く（v0.0.317 で ID のコントラストを実測し、ガラス+ダークの `filter: brightness(1.7)` を外したのと同じ問題）

### 9-4. 入力コンボ演出

#### デスクトップの実装

`App.tsx:10820` 付近。**`input` イベントの `inputType` で挿入 / 削除を判定し、`getCaretClientPoint()` でキャレットの画面座標を取って、そこに紙吹雪を出す。**

#### 移植可否

| 要素 | 移植 |
|---|---|
| `typing-combo-badge`（ランク C/B/A/S） | **運べる**（位置に依存しない） |
| `typing-combo-banner`（fire / mega / shipped / jackpot …） | **運べる** |
| `typing-combo-ring` | **運べる** |
| コンボ計数・ランク判定・途切れ判定 | **運べる**（`onChangeText` の差分で駆動） |
| **キャレット位置の紙吹雪** | **運べない** |

**運べない理由:** React Native の `TextInput` には**キャレットのピクセル座標を取る API が存在しない。** `onChangeText` は文字列全体、`onKeyPress` は日本語入力では当てにならない。

#### 回避策

紙吹雪の**出所を変える**。入力欄の上辺、画面端、送信ボタンの周り。

**モバイルではこの方が良い可能性が高い。** ソフトキーボードが画面の 4〜5 割を占めるためキャレット周辺はもともと窮屈で、演出は空いている上半分に出した方が映える。

#### 描画手段はむしろ強化される

ボイラープレートに **Skia + reanimated + worklets** が入っている（§3-3）。

- Skia のパーティクルは **UI スレッドで描ける**ので、JS スレッドが詰まっても演出が落ちない（不変条件 4）
- デスクトップ版は `comboLivePieces` で DOM 要素を管理しているが、Skia なら要素管理が不要
- `typing-combo-banner` の `@keyframes` も reanimated で置き換えられる

#### 自作 IME の件とは別件

**これに自作キーボードは要らない。** 2026-10-19 に見送ったのは「他のアプリでも使えるキーボード」の構想で、iOS のキーボード拡張がサンドボックスに閉じ込められ全画面演出が不可能、というのが理由だった。Ember の投稿画面は**アプリ自身の画面**であり、標準キーボードを使いながらアプリが自分の画面に演出を描ける。

#### 未解決: 変換中をコンボに数えるか

「こんばんは」と打って変換確定すると `onChangeText` は未確定の各打鍵でも発火し、確定時に文字列が置き換わる。デスクトップは `inputType` で挿入 / 削除を区別できたが **RN にはその情報がない。**

素直な解は「確定後の文字数差分だけで数える」だが、「変換を 1 回確定＝一気に 5 コンボ」になり手触りが変わる。**実機で触って決める**（§14-4）。

### 9-5. テーマと文字サイズ

- `theme/colors.js` / `theme/fontSize.js` を使う
- **ID の色はモード別パレット 2 本**を移植する（ライトは白に対して 7:1 以上、ダークは `#252526` に対して 5.5:1 以上。実測の最小値はライト 6.99:1 / ダーク 5.52:1）
- **`idColorMap` は「ID → 色」ではなく「ID → パレットの添字」**を持つ。テーマを切り替えても同じ人は同じ色相になる
- 文字サイズは板 / スレ / レスの 3 系統を残す（タブは廃止）

### 9-6. キャッシュ・オフライン・通信量

| データ | 置き場 |
|---|---|
| スレッド本文（dat）+ **バイト長** + **Last-Modified** | **SQLite**（`expo-sqlite`） |
| 設定・お気に入り・NG・既読 | **AsyncStorage**（§10） |
| AI モデル | **ファイルシステム**（`expo-file-system`）。**同期対象にしない** |

オフライン閲覧は「通勤前に監視スレを取得しておいて地下鉄で読む」を想定する。

#### デスクトップ版が既に持っている仕組み

`core-fetch` の `ThreadFetchOptions` / `ThreadFetchOutcome` にそのまま設計がある。

| 要素 | 内容 |
|---|---|
| `if_modified_since` | 前回の `Last-Modified` を付けると、更新が無ければサーバーが **304 を返し本文が流れない = 転送量 0**（コメントに「5ch.io / bbspink とも対応を実測済み」とある） |
| `allow_html_fallback` | dat が 404 のとき `read.cgi` の HTML を取り直す。過去ログを開くには必要だが、**「HTML は dat より何倍も重い」ので一括処理では切る** |
| `ThreadFetchOutcome.not_modified` | 304 が返った合図。`responses` は空なので呼び出し側はキャッシュを据え置く |

**モバイルでもこの 2 つは必須。** 特に `allow_html_fallback` は、ホームの「全件の新着チェック」（§8-1）では必ず切る。

#### モバイルで追加する: Range による差分取得（M1 から実装、2026-11-04 に実測して成立を確認）

**デスクトップでは「着手しない」判断だったが、モバイルは従量制回線なので前提が違う。** 1000 レスの dat は数百 KB あり、自動更新で毎回フル取得するとデータを食う。

**dat は追記専用**なので、保存済みのバイト長 `N` から差分だけ取れる。

```
1. キャッシュから N (保存済み dat のバイト長) と Last-Modified を取り出す
2. GET /dat/<id>.dat
     If-Modified-Since: <Last-Modified>
     Range: bytes=N-
3. 応答で分岐
   304 Not Modified      → 何もしない (転送量 0)
   206 Partial Content    → 本文をキャッシュに追記してパース
   200 OK                 → 全文で置き換える (サーバーが Range を無視した場合)
   416 Range Not Satisfiable → dat が縮んでいる。全取得し直す
   404 Not Found          → 過去ログ化。§9-10 へ
```

**必ず入れる防御:** **dat が縮む場合がある**（あぼーん、dat 整理）。この状態で 206 の差分を追記すると本文が壊れる。

- 206 で受けた断片が**レスの途切れた途中から始まっていたら**（行頭でない / 区切りが合わない）、**全取得し直す**
- パースに失敗したら全取得し直す
- 安全側に倒す。**壊れた本文を表示するより再取得する方が安い**

#### セルラーとの切り分け

| 項目 | Wi-Fi | セルラー |
|---|---|---|
| 自動更新間隔 | 短め | **長くする**（既定値を分ける） |
| 画像・サムネの自動取得 | する | **設定で切れるようにする** |
| OGP カードの取得 | する | 同上 |
| AI モデルのダウンロード | する | **既定で禁止**（§9-9） |

### 9-7. 同期

#### デスクトップの既存機能

Ember は**データフォルダのリダイレクト**で同期を実現している（方式は「クラウドストレージへの委譲」）。設定「アカウント」の文言:

> OneDrive / iCloud Drive / Google Drive 等の同期フォルダを指定すると、複数PCでお気に入り・NG・既読・認証設定を共有できます。設定は各PCで個別に行ってください（この設定自体は同期されません）。

実装の要点:

| 要素 | 内容 |
|---|---|
| 保存先の指定 | `location.json` の `dataDir`。**常に既定ディレクトリ配下に置き、同期フォルダには持ち込まない**（各マシンが共有フォルダの自分のマウントパスを指すため） |
| 環境変数 | `EMBER_DATA_DIR` |
| オフライン耐性 | `dir_is_usable()` が書き込み可否を実測し、**同期が未完了のクラウドフォルダや抜かれたドライブなら既定の場所へ自動フォールバック** |
| モデルの除外 | `models_base_dir()` が**意図的にリダイレクトを無視**。数 GB のモデルを容量制限のある同期フォルダに置かない |
| 書き込み | 一時ファイル + `rename` |

#### モバイルでは使えない

サンドボックス内のアプリが OneDrive / Dropbox の同期フォルダをファイルシステムとして掴めない。iOS の iCloud コンテナは iOS 限定で、しかもデスクトップ版のファイルはユーザーが選んだ任意のフォルダにあるため、**両者は同じ場所で出会えない。**

**ただし同期の実体は「ファイルシステム上のプレーンな JSON」で、書き込みがアトミックに設計されている。スキーマが既に交換フォーマットとして確定している。**

#### 段階

| 段階 | 手段 |
|---|---|
| **M1〜M3** | **同期なし。** 共有シートでの URL 受け渡し（Ember は既に URL 貼り付けでスレを開ける）と、設定の JSON 手動エクスポート / インポートのみ |
| **M4（入れるか未決、§14-11）** | **LAN 直接同期。** 同一 Wi-Fi 上で QR ペアリングし HTTP で JSON 直送。サーバー不要・費用ゼロ・データが外に出ない。**自宅 Wi-Fi を検出したら自動同期**（出る前に引っ張り、帰ったら書き戻す。既読は帰宅後の反映で十分なのでリアルタイム性は要らない） |
| **やらない** | **常時同期サーバー。** 技術的には簡単（Cloudflare Workers + KV）だが、ユーザーの 5ch 閲覧履歴が端末外に出る。Priveat で「食事記録は端末の外に出ません」を売りにしている設計思想と衝突する |

**#11 で LAN 直接同期を落とすと、初版に同期は存在しなくなる**（URL の共有シート受け渡しと手動 JSON のみ）。これが #1「作るかどうか」の保留理由に直結している — §14 の「#1 について」。

#### 既存設計から引き継ぐ判断

1. **モデルファイルは同期しない**
2. **同期の設定自体は同期しない**（`location.json` をローカル固定にしているのと同じ理由。モバイルのペアリング設定も端末ごと）
3. **同期先が使えないときのフォールバック**（モバイルでは「LAN に繋がっていない」が同じ問題）
4. **書き込みは一時ファイル + rename**（不変条件 5）

#### 同期しないもの

タブ構成（モバイルにタブがない）、レイアウト・文字サイズ・ガラス設定（デバイスごとに最適値が違う）、**ピクセルのスクロール位置**（§10-1）。

**認証設定は同期しない（決定、2026-11-04）。** デスクトップ版は既に同期対象に含めているが、持ち歩いて紛失・盗難のリスクがある端末とでは信頼境界が違う。理由は 4 つ:

1. 端末は紛失・盗難がある
2. 上の「**同期の設定自体は同期しない**」と同じ判断
3. Ronin / BE の再入力コストは年 1 回程度で、失うものに比べて小さい
4. **Keychain / Keystore に置いたものを LAN に流すのは、設計として一貫しない**

### 9-8. 通知

#### デスクトップの既存機能

**Discord Webhook 経由の通知が既に実装済みで、既にスマホに届いている。**

```rust
struct NotifyConfig {
    enabled: bool,
    webhook_url: String,
    /// Discord のユーザーID (任意)。入っていればメンション付きで送るので、
    /// サーバーの通知設定が「@メンションのみ」でもプッシュが飛ぶ。
    discord_user_id: String,
    /// 巡回間隔 (分)
    interval_min: u32,
}
```

設定項目は「自分宛のレスを通知する」「Discord ユーザーID (任意)」「巡回間隔 (分)」、ボタンは「テスト送信」「今すぐ巡回」。

**つまり「PC で書いたレスへの返信が外出先のスマホに届く」は今日すでに実現している。**

#### モバイル版が足す価値

| | なぜ価値があるか |
|---|---|
| **PC が落ちていても通知が来る** | 現状は巡回するデスクトップ版が起動している必要がある。**ここが唯一の本質的な差** |
| **通知をタップしてそのままスレへ入れる** | 現状は Discord → URL をコピー → どこかで開く |
| Discord の設定が不要 | Webhook URL の用意が要らない |

#### 方式の比較

| 方式 | 確実性 | PC が落ちていても | 実装コスト |
|---|---|---|---|
| **既存の Discord Webhook** | **高**（Discord のプッシュ基盤） | × | **0** |
| ネイティブのバックグラウンド取得 + ローカル通知 | **低**（iOS は OS 裁量。最短 15 分間隔・実行保証なし） | ○ | 中 |
| 自前のプッシュサーバ | 高 | ○ | 高 + 運用費 + プライバシー |

#### バックグラウンド巡回の仕組みと限界（Expo SDK 58 の公式ドキュメントによる）

M4 でネイティブ通知をやる場合、巡回には **`expo-background-task`**（+ `expo-task-manager`）を使う。Android は WorkManager、iOS は BGTaskScheduler。

**ドキュメントに明記されている制約:**

| 項目 | 内容 |
|---|---|
| 実行間隔 | `minimumInterval` は**不正確**。既定は 12 時間ごと、**最小 15 分**。「システムが実行間隔を制御し、指定値は最小の遅延として扱われる。タスクは正確なスケジュールでは実行されない」 |
| **iOS の実態** | **「短い間隔はしばしば無視される。システムは通常、夜間などの特定の時間帯にバックグラウンドタスクを実行する」** |
| 実行条件 | **バッテリーに十分な充電がある（または給電中）かつネットワークが利用可能**でなければ実行されない |
| 強制終了 | **「ユーザーがアプリを kill するとバックグラウンドタスクは停止する」。** iOS でアプリスイッチャーからスワイプすると完全に終了する（Android は最近のアプリ一覧から消しても完全には止まらない。ただしベンダ差がある） |
| 再開 | システムがアプリを停止した場合や端末が再起動した場合は、アプリ再起動時にタスクも再開される |
| **ワーカーは 1 本** | **「両プラットフォームとも単一のワーカーを使う。最後に登録したタスクが実行間隔を決める」** |
| 実行時間の上限 | 明示なし。iOS は「数分間実行できるが、システムはいつでも中断できる」 |
| **シミュレータ** | **BGTaskScheduler は実機でしか使えない。** テストには実機が必要 |

**iOS の設定**（CNG / prebuild を使えば自動で入る）:

```xml
<key>UIBackgroundModes</key><array><string>processing</string></array>
<key>BGTaskSchedulerPermittedIdentifiers</key>
<array><string>com.expo.modules.backgroundtask.processing</string></array>
```

**設計上の結論:**

- **5ch の新着を数分以内に知らせる用途には使えない。** iOS は「夜間などの特定の時間帯」に寄せてくる。実況スレの新着通知は**この仕組みでは成立しない**
- 使えるのは「**しばらく見ていない間に溜まった分を、次に端末を触るより前に取っておく**」という用途。オフライン閲覧（§9-6）の先読みと相性が良い
- **ワーカーが 1 本しかない**ので、巡回と先読みを別タスクとして登録すると間隔が干渉する。**1 つのタスクにまとめる**
- **実機でしかテストできない**ので、CI では検証できない

#### 段階

1. **M1〜M3 では通知を実装しない。** 既存の Discord 通知が既に届いているので、**モバイル版は「Discord の通知をタップした後の着地点」として機能すれば十分。** 深いリンク（`ember://thread/...` 等）で該当レスを開けるようにするだけでよい
2. **M4 でネイティブのローカル通知を足す。** PC が落ちているときのベストエフォートとして。Discord と併用し、どちらかが届けばよい形にする
3. **自前のプッシュサーバは作らない**

**「必ず届く」とは謳わない。** これは最初に決めておく。

### 9-9. ローカル LLM

#### モバイルに載るモデル

Ember のカタログ（`ai-models.json`、11 本）のうち載るもの:

| モデル | サイズ | 用途 | 可否 |
|---|---|---|---|
| `bge-m3-zeroshot-v2-q4km` | **0.44GB** | **NG 判定**（分類器・ctx 8192） | ◎ |
| `lfm2-5-1.2b-jp-q4km` | **0.73GB** | 要約（日本語特化・ctx 128K） | ◎ |
| `gemma3-1b-it-q4km` | 0.81GB | 要約 | ◎ |
| `hy-mt2-1.8b-q4km` | 1.13GB | 翻訳 | ○ |
| `qwen35-2b-q4km` | 1.28GB | 要約 | ○ |
| `qwen35-4b-q4km` | 2.74GB | 要約・返信 | △（8GB 機のみ） |
| `gemma4-e2b-it-q4km` | 3.11GB | 要約 | △ |
| 4.98GB 以上の 4 本 | — | — | **×** |

**用途 4 種（summary / reply / translation / ng）のうち 3 種が成立する。**

#### エンジンは二刀流（FeedOwn の実測による）

FeedOwn の `ai/llama/models.js` のコメント:

> Phase F (Gemma 3 1B-IT vs LFM2.5 1.2B summary bench on A15) showed **executorch is 55% faster** on the general-purpose path, so general LLM stays on executorch.

- **汎用（要約・生成）→ `react-native-executorch`**（A15 で 55% 速い）
- **`llama.rn` → GGUF にしかないモデル専用。** FeedOwn の本番スコープは翻訳特化の Hy-MT2 1.8B Q4_K_M の 1 本のみ

**`hy-mt2-1.8b-q4km` は Ember のカタログにも入っている**（同じモデル・同じ量子化）。LFM2.5 1.2B も両方にある（Ember は GGUF、FeedOwn は `.pte`）。

#### RAM 制約（FeedOwn の実機実測）

- iPhone 13 mini (A15, 4GB) 実測: **Metal working set = 2863MB**、アプリのベースライン + KV/compute ≈ 1GB、**安全な重みの上限は 4GB 機で約 1.8GB**
- `RAM_TIER` は 4GB / 6GB / 8GB の 3 段階。iOS の `Device.totalMemory` は物理 RAM の約 90% を返すため、閾値は各クラスのやや下に置く
- `canRunOnDevice()` が判定し「Needs ~4GB+ RAM (this device: 3.6GB)」という文言を返す
- `DEFAULT_MAX_INPUT_CHARS = 4000`

#### NG 判定の方式（未決・要ベンチ）

| 案 | 内容 | 利点 / 欠点 |
|---|---|---|
| **1. `bge-m3-zeroshot` を移植** | 専用の zero-shot entailment 分類器 0.44GB | 1 件あたり安い可能性が高い / **2 本目のモデルを積む必要がある** |
| **2. FeedOwn の `judge.js` 方式** | 汎用モデルに A/B を 1 トークンだけ生成させ確率を読む | **モデルが 1 本で済む**（4GB 機の重み上限 1.8GB の中で要約用と分類器を同時に載せるのは苦しい） / 1 件あたりは高い可能性 |

**推測で決めず、FeedOwn の `benchmark.js` で測ってから決める**（§12-0）。1000 レスの一括判定では案 1 が勝つ可能性が残る。

#### `judge.js` に記録されている実機の地雷（必ず読むこと）

- **`logit_bias` は使うな** — llama.rn の `JSIParams.cpp` が `std::vector<llama_logit_bias>` を token ID で添字アクセスしており、渡すと **OOB 書き込みでネイティブクラッシュ**（iPhone 13 mini で再現済み）
- **`completion_probabilities` は末尾を読め** — 非並列 completion で `generated_token_probs` が completion 間で clear されず、`[0]` は「この ctx で最初に n_probs 付きで生成したトークン」の確率を返し続ける（4 モデル全件で同一確率として再現）
- **サンプラの切り捨てを全部切れ**（`top_k 0 / top_p 1.0 / min_p 0.0 / typical_p 1.0`）— デフォルト（top_k 40 / top_p 0.95 / min_p 0.05）のままだと弱い側のラベルが 0 に落ちて人工的に飽和する（iPhone 13 mini 実測: A 0.6147 / B 0.3853 がちょうど 1.0 に足し上がっていた）

#### 要約の罠

**生成ではなくプロンプト処理（prefill）が重い。** 1000 レスのスレは 10 万トークン級で、スマホで頭から食わせると発熱して終わらない。

**回避: 全文要約をやめて差分要約にする。**「未読 50 件を 3 行で」。技術的に軽いだけでなく**モバイルの使い方そのもの**で、デスクトップ版の機能をそのまま持っていくより良くなる。

#### その他

- モデル配布は審査上問題ない（実行コードではなく重みデータ。アプリバンドルに同梱しない）
- **ダウンロードは Wi-Fi 限定をデフォルトに**（1GB をモバイル回線で落とさせない）
- ストレージ UI — サイズ表示と削除導線を目立たせる
- 発熱でのバックオフ機構（不変条件 4）

### 9-10. 異常系とエラー表示

デスクトップ版の `FetchError` は `Request` / `Url` / `HttpStatus(status)` / `Parse(String)` の 4 種。モバイルでも同じ分類で受ける。

**原則: キャッシュがあるなら、取得に失敗しても表示を消さない。** 読めていたものが読めなくなるのが最悪の体験（不変条件 3 と同じ発想）。

| 状況 | 検出 | 画面の振る舞い |
|---|---|---|
| 通信失敗（圏外・タイムアウト） | `Request` | **キャッシュを表示したまま**、トーストと再試行ボタンを出す。画面を空にしない |
| 更新なし | 304 / `not_modified` | 何も変えない。「更新なし」を控えめに表示 |
| dat が 404（過去ログ化・dat 落ち） | `HttpStatus(404)` | `read.cgi` フォールバックを試す（§9-6）。**一括更新中は試さない。** 取得できたら「過去ログ」バッジを出し、**投稿を無効化**。取れなければキャッシュを読み取り専用で見せる |
| dat が縮んだ | 416 / パース不整合 | 全取得し直す（§9-6）。ユーザーには見せない |
| スレが 1000 到達 | レス数 | **投稿ボタンを無効化し、理由を明示。** 次スレ検索はしない（§12-5） |
| パース失敗 | `Parse` | **そのレスだけ生テキストで出す。** スレ全体を失わせない |
| 認証切れ | 投稿時の応答 | 再ログインを促す。本文は保持する（「閉じても本文を残す」の思想） |
| 書き込み規制・エラー | 投稿時の応答 | **5ch 側の文面をそのまま出す。** 独自に言い換えない（規制の理由は原文が一番有用） |
| ストレージ不足 | モデル DL 前 | 事前に空き容量を確認し、必要量を出して中止 |
| 端末 RAM 不足 | `canRunOnDevice()` | 「Needs ~4GB+ RAM」相当の文言（§9-9） |

### 9-11. ログとエラー処理の規約

デスクトップ版の規約（`CLAUDE.md` / `.claude/rules/react.md`）をそのまま引き継ぐ。

- **`.catch(() => {})` は禁止。** エラーは必ず `console.warn` でログを残す
- **Cookie 値（`Be3M`, `Be3D`, `sid`）をログに出さない**（§11-4）
- 本番ビルドで verbose なログを出さない
- **クラッシュレポートの外部送信はしない。** §9-7 と同じ思想（閲覧履歴を端末外に出さない）。必要なら端末内のログファイルに留め、ユーザーが自分で送れる形にする

## 10. データモデル

### 10-1. 永続化するもの

| データ | 型 | 置き場 | 同期 |
|---|---|---|---|

### 10-2. 書き込みの安全性

**すべての永続化で一時ファイル + rename 相当の手順を取る**（不変条件 5）。デスクトップ版は `fs::write` が先に 0 バイトへ切り詰めるため、書き込み中にプロセスが落ちると壊れた JSON が残り、次回の読み込みで**既読やお気に入りが丸ごと消える**事故を経験している。

### 11-1. User-Agent


**これは必ず名乗る。** 2ch / 5ch が専ブラに自己申告させるために定めた慣習で、善意の証拠になる。隠すと立場が弱くなる（§13-2）。

### 11-2. エンドポイント

| 用途 | 経路 |
|---|---|
| 板一覧 | `bbsmenu.json` |
| スレ一覧 | `subject.txt` |
| スレ本文 | `/dat/<id>.dat` |
| 投稿 | `test/bbs.cgi` |
| HTML の読み取りページ | `/test/read.cgi`（URL の扱いと Referer 用） |

### 11-3. 文字コード

**レスポンスは Shift_JIS。** `arrayBuffer()` で受けてからデコードする。Hermes に `TextDecoder('shift_jis')` が無いので純 JS の実装が必要（§3-4）。

**決定（2026-11-04、M0 で実測）: `encoding-japanese` 2.5.0 を使う。** 実装は `apps/mobile/src/lib/sjis.js`。

| 検証 | 結果 |
|---|---|
| 実データとの一致 | AA 長編板の 899KB dat / ニュース速報の 189KB dat / subject.txt 2 本（計 1.08MB）で、Python の `cp932` デコードと **1 文字も違わず一致** |
| デスクトップ版との一致 | 全バイト空間 23,692 ケースを `encoding_rs::SHIFT_JIS`（デスクトップ版が使うもの）と突き合わせ。**差が出るのは未定義バイト・ユーザー外字（PUA）・不正バイト後の復帰だけ**で、実在する文字はすべて一致 |
| 速度 | 899KB の dat で **21.9ms**（デスクトップ Node）。実機はこれより遅いので、大きいスレは分割して回す（不変条件 4） |

#### 落とし穴（必ず読むこと）

**`encoding-japanese` は不正なバイト列に出会うと、置換文字 `?` を 1 個出して直後の 1 バイトを一緒に飲み込む。** `encoding_rs` は置換文字の後に後続バイトを ASCII として復帰させるので、ここが違う。

本文の末尾が 2 バイト文字の途中で切れていると、**直後の区切り `<>` の `<` が食われて `>` だけが残り、レコードの構造が壊れる。**

```
バイト列 [0x82, 0xA0, 0x82, 0x3C, 0x3E, 0x41]  （「あ」+ 切れたリードバイト + <> + A）
         → "あ?>A"       ← 区切り `<>` が消えている
```

**対策: dat / subject.txt は必ずバイト列のまま区切ってから、フィールド単位でデコードする。** 文字列に直してから `split('<>')` してはいけない。

安全である根拠: Shift_JIS のトレイルバイトは `0x40-0x7E` と `0x80-0xFC`。区切りに使う LF (`0x0A`) / `<` (`0x3C`) / `>` (`0x3E`) / TAB (`0x09`) は**いずれも `0x40` 未満なのでトレイルバイトになり得ない。** したがってこの 4 バイトでの分割が多バイト文字の内部を割ることはない。

実装は `apps/mobile/src/lib/bytes.js`、テストは `__tests__/lib/bytes.test.js`。**この挙動を固定するテストを `__tests__/lib/sjis.test.js` に置いてある**（直すためではなく、忘れないため）。

### 11-4. 認証

Ronin（浪人）/ BE / どんぐり / UPLIFT。デスクトップ版は `core-auth`（395 行）+ IPC 17 本。

**Cookie 値（`Be3M`, `Be3D`, `sid`）は DEBUG 以上でログに記録しない**（デスクトップ版と同じ規約）。

### 11-5. 投稿フロー

**書き込み確認の中間ページに対応する必要がある。** Cookie の扱い、Shift_JIS のフォームエンコード、確認ページの検出と再送。**作業量の半分以上がここ**（§12-2）。

### 11-6. URL の正規化

ユーザー入力・外部由来の URL は正規化を通す（デスクトップの `normalize_5ch_url()` 相当）。投稿先は 5ch ドメインに限定検証する。

### 13-4. ストア配布のリスクと配布方針（決定）

**審査は障害ではない。** ユーザーは App Store に 9 本公開中（うち **17+ が 2 本**）、Google Play にも公開実績がある。5ch 専ブラは全て 17+ で通っている（§15-1）。

|---|---|---|---|

#### #1 について — 相乗効果の評価（2026-11-04）

**この評価は #1 が決着した後も有効。** #1 は「作って判断する」で決まったが、**#13「リリースするかどうか」はこの評価の上に残っている。** 以下はそのまま読むこと。

**ユーザーが着手を迷っている理由は「デスクトップ版との相乗効果を感じない。データ同期もできない。LAN 同期は現実的でない」。** 本文書を読み直して検証したところ、**この指摘は正しい。** #1 を判断するときはここから読む。

**1. 同期は「やらない」のではなく構造的に成立しない。** デスクトップ版の同期方式はクラウドストレージへの委譲で、`location.json` の `dataDir` を OneDrive / iCloud Drive の同期フォルダへ向けるもの（§9-7）。モバイルはサンドボックスでその同期フォルダをファイルシステムとして掴めず、しかもデスクトップ版のファイルは**ユーザーが任意に選んだフォルダ**にあるため、両者が同じ場所に居合わせない。**OS の制約で、埋められない。**

**2. したがって初版に同期は存在しない。** §9-7 の段階表は M1〜M3 が「同期なし（URL の共有シート受け渡しと手動 JSON エクスポート / インポートのみ）」、LAN 直接同期は M4 で**採否自体が未決**（#11、本文書の推奨は落とす）、常時同期サーバーは却下。**LAN を落とせば初版の同期はゼロ。** ユーザーは LAN 同期を「現実的でない」と判断している。

**3. 計画書はもともと相乗効果を根拠にしていない。** §6-1 がモバイル版を「デスクトップ版の縮小ではなく**通知駆動の実況・追跡アプリ**」= 別アプリとして位置づけている。そして §6-3「モバイルで増える価値」の 6 項目（PC が落ちていても追える / 通知から直接スレへ / オフライン閲覧 / 共有シート / カメラロールから投稿 / 実況モード）は、**すべてモバイル単体の価値で、同期に依存するものがひとつもない。**

**4. 実在する相乗効果は 2 つだけで、どちらも弱い。**

| | 内容 | 評価 |
|---|---|---|
| 通知の着地点（§9-8） | デスクトップ版の Discord 通知をスマホで受け、タップでモバイルアプリの該当レスへ着地する。同期不要で成立する唯一のもの | **弱い。** Discord をタップしてブラウザで開くのと大差ない |
| コードと知識（§5-3 / #8 / #10） | `core-parse` の TS 版、AA 検出のデスクトップ逆輸入、ID ハッシュ（デスクトップ側の出現順依存も直る） | **開発側の都合であり、ユーザー体験の相乗効果ではない** |

**5. 相乗効果を作れる手は 1 つだけ存在する（却下カテゴリ、採否保留）。** **E2E 暗号化した blob を dumb な置き場に置く方式**（Cloudflare Workers + KV、無料枠あり）。端末で暗号化・復号するのでサーバーには判別不能なバイト列しか乗らず、§9-7 の却下理由「**平文で**閲覧履歴が端末外に出る」を直接解消する。ただしこれは「常時同期サーバー」の一種で**「再提案しないこと」に入っている**。鍵の管理と紛失時の復旧、運用の責任が増えるのも事実。**2026-11-04 に一度提案し、ユーザーの採否は保留。これ以上は押さない。**

**結論: 相乗効果を着手の条件とするなら、現計画はその条件を満たさない。** 計画書が位置づけているのは独立したモバイル専ブラで、§15-1 の通り **App Store に 8 本以上が現役で並ぶ市場**に、`App.tsx` 17,664 行 + `styles.css` 8,725 行 = **26,389 行の UI 再実装**（§4-3）で参入する話になる。「自分のデスクトップ版が良くなる」という動機が無い状態では、投資に対する見返りを説明できない。

**M0（§12-0）を回してもこの判断材料は増えない。** M0 が解くのは Shift_JIS・流用率・NG 方式で、相乗効果はそこに含まれない。**迷いの中身が相乗効果である限り、M0 は判断の前倒しにならない。**

## 16. テスト戦略

### 16-1. 3 層構成

| 層 | 道具 | 対象 |
|---|---|---|
| **単体** | **jest-expo**（ボイラープレートに同梱。`npm test` = `jest --passWithNoTests`） | dat パーサ、`subject.txt` パーサ、NG 判定、**AA 検出**、既読計算、**Range の差分マージ**、SJIS デコード |

| **手動（実機）** | — | ジェスチャの手触り、AA の見た目、ガラス効果、**バックグラウンド巡回**（シミュレータ不可、§9-8）、発熱 |

### 16-2. デスクトップ版から引き継ぐ思想

デスクトップ版は Playwright で **186 項目**のスモークを回している。引き継ぐべき原則は 2 つ。

1. **素通りしないアサーションにする。** 「エラーが出ない」ではなく、**本物の入力と実際の結果**を検査する（デスクトップでは実際のキー入力とスクロール位置の実測値で確認している）
2. **破壊テストで担保する。** テストを書いたら、**対応する実装を意図的に壊してテストが落ちることを一度確認する。** 落ちなければそのテストは穴

### 16-3. 毎リリース検査 5 項目の Maestro フロー

| # | 項目 | フロー |
|---|---|---|
| 3 | **`>>` ジャンプ** | スレを開く → `>>1` をタップ → ポップアップに 1 レス目が出る → **ポップアップ内の `>>` をタップして連鎖する** |
| 4 | **ID シート** | ID をタップ → 件数とレス一覧が出る → タップで該当レスへジャンプ |
| 11 | **AA** | AA を含むレスが**折り返されず、折りたたまれていない**ことを確認 |
| 12 | **NG 漏れ** | NGID を登録 → **本文 / 参照ポップアップ / ID シート / 被参照一覧 / 検索結果の 5 箇所すべてで消えている**ことを確認 |
| 13 | **ソート維持** | ソートを変更 → 更新 → **順序が保たれている**ことを確認 |

**表示密度を入れたら（M4、§8-4）、3 / 11 / 12 は密度ごとに回す。** 密度は描画経路を増やすので、片方だけ通っても担保にならない。

### 16-4. fixture

**実 dat を取得してテスト用に固定する。** SJIS のバイト列をそのまま置く（デコードのテストに必要なので、UTF-8 に変換してはいけない）。

AA を含むレス、1000 レス到達済みのスレ、あぼーんで縮んだ dat の 3 ケースは**必ず fixture に含める**。

### 16-5. CI（2026-11-04 に設置）

`.github/workflows/mobile.yml` を追加した。**`apps/mobile/**` が変わったときだけ回し、既存の `ci.yml` / `release.yml` には触っていない**（§3-7）。中身は `eslint src/ --quiet` → `jest --ci` → `expo export --platform android`（Hermes バイトコードまで通すのでバンドルの壊れを捕まえる）。



**ボイラープレートの `.github/workflows/main.yml` はそのまま使えない。** 現状は `actions/checkout@v1` / `setup-node@v1` で **node 12.x**、`expo/expo-github-action@v5` に `expo-version: 4.x`、コマンドは **`expo publish`（classic updates、現在は EAS Update に置き換わっている）**、トリガーは `sub` ブランチ。**書き直す。**

- Ember 本体の CI（cargo / tsc / Playwright）とは**別ワークフロー**にする（§3-7）
- CI で回すのは **lint + jest**。Maestro は実機 / エミュレータが必要なので、**ローカルまたは EAS 側で回す**
- **バックグラウンド巡回は CI で検証できない**（実機専用、§9-8）

## 17. リリースと配布

### 17-1. EAS Build + EAS Submit

**FeedOwn の `apps/mobile/eas.json` と同じ構成に倣う。**

**iOS / Android を同時に申請する**（§13-4 の決定）。`production` プロファイルで両プラットフォームをビルドし、`submit` で両ストアへ出す。iOS ビルドを EAS に投げる構成なので、**EAS の有料プランの課金が前提**になる（§14-12）。

**`app.json` に入る確定値:** `name` は `Ember`（`CFBundleDisplayName` 相当）、`ios.bundleIdentifier` と `android.package` はどちらも `net.votepurchase.ember`。**ストア掲載名は「Ember 掲示板ブラウザ」で、`app.json` の `name` とは別**（App Store Connect / Play Console 側で設定する）。

```json
{
  "cli": { "version": ">= 16.28.0", "appVersionSource": "remote" },
  "build": {
    "base": { "node": "22.19.0" },
    "development": {
      "extends": "base", "developmentClient": true,
      "distribution": "internal", "channel": "development",
      "ios": { "simulator": false }, "android": { "resourceClass": "large" }
    },
    "preview": {
      "extends": "base", "distribution": "internal", "channel": "internal"
    },
    "production": {
      "extends": "base", "channel": "production",
      "ios": { "autoIncrement": true },
      "android": { "autoIncrement": true, "resourceClass": "large" }
    }
  },
  "submit": { "production": {} }
}
```

| 設定 | 意味 |
|---|---|
| `appVersionSource: "remote"` | バージョンを EAS 側で管理する。`app.json` に書かない |
| `autoIncrement` | ビルド番号を自動で上げる |
| `channel` | **ビルドプロファイルと OTA チャンネルを対応させる**（development / internal / production）。`expo-updates` はこのチャンネルへ配る |
| `ios.simulator: false` | development ビルドも実機向け（§9-8 の制約と整合）。**現在の `apps/mobile/eas.json` は `true`。** 2026-11-04 からユーザーの判断でシミュレーター上で開発しているため。実機の確認に入るときに切り替える |

### 17-2. デスクトップ版との違い

| | デスクトップ | モバイル |
|---|---|---|
| 手順 | `scripts/release.sh` → `scripts/release_finish.sh` | `eas build` → `eas submit` |
| バージョン | `package.json` / `tauri.conf.json` / `Cargo.toml` / updater の 4 箇所を同期 | **EAS の remote 管理** |
| 配布 | GitHub Release + `latest.json` + 自前アップデータ | **App Store / Google Play + `expo-updates`** |
| 緊急修正 | 再ビルドして再配布 | **OTA（ネイティブを含まない変更のみ）** |
| リリースノート | 100〜150 文字 / 1〜3 文 / `- ` 始まり / 原因や内部経路は書かない | **同じ規約を踏襲する** |

### 17-3. OTA の注意

`expo-updates` は **JS バンドルだけを差し替える。** ネイティブモジュール（`llama.rn` / `expo-blur` / `expo-sqlite` / `expo-background-task` 等）を追加・更新したら**ストア審査が必要**。

OTA で直せるもの: UI、AA 検出の閾値、NG のロジック、プロンプト、文言。
OTA で直せないもの: 依存の追加、権限の変更、ネイティブ側の不具合。

### 17-4. ストア申請時に決めること

#### アイコン（2026-11-04 決定・作成済み）

**デスクトップ版と同じ炎のアイコンを使う。** 元は `apps/desktop/src-tauri/icons/icon.png`（512x512 RGBA）。

| 生成物 | 用途 | 中身 |
|---|---|---|
| `assets/images/icon.png` | iOS / 汎用 | **1024x1024 RGB（透過なし）。** 炎を占有率 78% で `#0b0d12` の上に置いた |
| `assets/images/adaptive-icon.png` | Android の前景 | 1024x1024 RGBA。炎を占有率 **58%** に収めた（安全圏は中央 66% の円）。背景色は `app.json` の `#0b0d12` |
| `assets/images/splash-icon.png` | スプラッシュ | 1024x1024 RGBA。炎を占有率 42%（`contain` で中央に置かれる） |

**作り方（単純な拡大ではない）。** 元画像は実質 1 色（`#F54011`）の炎のシルエットで、中間アルファは全体の 2.3% しかない縁のアンチエイリアスだけ。512 → 1024 をそのまま拡大すると縁が鈍るので、**アルファをマスクとして取り出し、拡大してから縁の遷移を締め直し、単色で塗り直した。** ベクタから起こしたのと同等の鮮明さになる。再生成が必要なら同じ手順を踏むこと。

**背景色に `#0b0d12` を選んだ理由。** iOS のアイコンは**アルファチャンネルを持てない**ので背景を決める必要がある。`#0b0d12` はランディングページ（`apps/landing/src/styles.css` の `--bg`）と同じで、**Ember が公の場で自分を見せている背景**。ブランド色 `--brand: #ff6a3d` も炎と同系。

**ボイラープレートのロゴは削除した**（`logo.svg` 704KB / `logo-lg.png` 528KB / `logo-sm.png` / `splash.png`）。`logo.svg` は metro に SVG トランスフォーマを入れていないため画像アセットとしてそのままバンドルに乗っており、しかもどこからも参照されていなかった。**差し引きでバンドルから約 1.2MB 減った。**

**未着手:** iOS 18 のアイコン変種（`ios.icon` の `dark` / `tinted`）は作っていない。単一アイコンでも問題なく出せるが、入れると iOS 18 のホーム画面で馴染みがよくなる。
