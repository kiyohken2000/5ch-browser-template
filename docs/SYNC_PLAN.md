# モバイル版とデスクトップ版のデータ同期（調査と設計案、2026-11-14）

モバイル版（`apps/mobile`）とデスクトップ版（`apps/desktop`）の間で、設定・既読・お気に入りスレ・
「ここまで読んだ」などを同期したい、というユーザーの要望を受けて調べた結果をまとめる。

**実装の仕様は `docs/SYNC_IMPLEMENTATION.md` にある。実装するセッションはそちらを読む。**
この文書は、方式を選んだ経緯と却下した案の記録。§5・§7・§8 の細部は、仕様書のほうが新しい。

**この文書は調査と設計案で、実装の承認はまだ無い。** 着手の前に §9 の「ユーザーが決めること」と §10 の先頭の確認を
ユーザーに確かめること（CLAUDE.md / memory の「実装着手前に必ず確認を取る」）。

## 1. 結論

- **運び方は「利用者自身の Google ドライブを API で使う」方式にする**（§7）。ユーザーの希望（2026-11-14）。
  開発者のサーバーを通らず、全 OS で自動かつ双方向に動く。
- **中継サーバー方式は却下された（2026-11-14）。再提案しない。**
- **同期の中身（共通の形式とマージの規則）は、運び方と関係なく要る。** 作業の大半はここにある（§5）。
  どちらのアプリも、お気に入りや NG を消すと行ごと消えるので、消した記録を残す仕組みを足す必要がある。
- **最初に確かめること:** Windows / Mac / iOS / Android のアプリから、同じ Google ドライブの領域が
  見えるか（§10 の先頭）。これが成り立たないと方式が変わる。

## 3. 現状: 両アプリのデータの持ち方

### 3-1. 保存場所

| | デスクトップ | モバイル |
|---|---|---|
| 主な保存先 | `core-store` の JSON（データフォルダ）と、WebView の localStorage（`desktop.*`） | AsyncStorage（`ember.*`、`src/lib/storage.js` の `KEYS`） |
| 既存の同期 | データフォルダを OneDrive などの同期フォルダへ向ける機能（`location.json` の `dataDir`）。**複数 PC の間だけ** | なし |
| 壊れたときの備え | 一時ファイル + rename | 大事なキーは影キー（`.bak`）へ先に書く |

デスクトップの localStorage のうち一部（書き込み履歴、最近開いたスレ、名前・検索の履歴、曖昧 NG のルールなど）は
`data/<名前>.json` が実体で、localStorage は副本（`App.tsx` の `UI_JSON_FILES`、`save_ui_json`）。
同期で書き換えるときは**ファイルと副本の両方**を更新する必要がある。読んでいた位置（`desktop.scrollPositions.v1`）は
localStorage だけにある。

### 3-2. データごとの対応

型は両方のソースで確かめた。「対応」は変換の難しさ。

| データ | デスクトップ | モバイル | 対応 |
|---|---|---|---|
| お気に入りスレ | `favorites.json` の `threads[]`: `{ threadUrl, title, boardUrl }` | `favorites.v1`: `[{ threadId, threadUrl, boardUrl, boardName, title, totalCount }]`（新しい順） | 易 |
| お気に入り板 | `favorites.json` の `boards[]`: `{ boardName, url }` | `boardFavorites.v1`: `[{ name, url, board, host }]` | 易 |
| 既読（何番まで読んだか） | `read_status.json`: `boardUrl → threadKey → lastReadNo`。**前進のみ**。時刻なし | `watchList.v1` の各行の `lastSeenCount`（と `totalCount`） | 易（大きいほうを採る） |
| ここまで読んだ | `read_marker.json`: `boardUrl → threadKey → no`。解除できる。**時刻なし** | `readMarkers.v1`: `threadId → { lastReadNo, totalCount, updatedAt, manualAt }`。`manualAt` があるものだけが印 | 中（デスクトップに時刻が要る） |
| 読んでいた位置 | `desktop.scrollPositions.v1`: `スレの URL → レス番号`。**時刻なし、件数の上限なし** | `scrollPositions.v1`: `threadId → { no, at }`（レス番号、最大 300 件） | 中（両方レス番号。デスクトップに時刻が要る） |
| NG（ワード / ID / 名前 / スレタイ） | `ng_filters.json`: `words` / `ids` / `names` / `thread_words`。要素は文字列か `{ value, mode, match, disabled, excludeNo1, addedAt }` | `ngFilters.v1`: `words` / `ids` / `names` / `threadWords`。要素は `{ value, mode, chainId, match, addedAt }` | 易（§9-7 で確認済み） |
| 強調表示 | `highlight_filters.json`（`HlEntry = { value, color, disabled, titleOff, addedAt }`） | `highlights.v1` | 易 |
| 曖昧 NG のルール | `desktop.ngAiRules.v1`: `{ id, predicates, threshold, disabled, addedAt }` | `aiSettings.v1` の `rules` | 易 |
| 画像 NG | `ng_image_filter.json` | `imageNg.v1` | 未確認（ハッシュの方式が同じか） |
| 書き込み履歴 | `desktop.myPosts.v1`（実体は `data/my_posts.json`）: `スレ → [{ no, at, title, body }]`。**レス番号で自分のレスを見分ける** | `myPosts.v1`: `[threadRef + { message, at }]`（最大 50）。**レス番号を持たず、本文と時刻の照合で見分ける**（`findMyResNumbers`） | 中（下の注） |
| 画像のアップロード履歴 | `upload_history.json`: `entries[]` = `{ sourceUrl, thumbnail, pageUrl, fileName, uploadedAt }`（最大 20） | `uploadHistory.v1`: `[{ sourceUrl, thumbnail, pageUrl, fileName, … }]`（最大 20） | 易（時刻の項目名と形式は実装時に確認） |
| 最近開いたスレ | `desktop.recentOpenedThreads.v1`: `FavoriteThread + { updatedAt }` | `recentOpened.v1`（最大 100） | 易 |
| 名前の履歴 / 検索の履歴 | `desktop.nameHistory.v1` / `desktop.searchHistory.v1` | `nameHistory.v1` / `searchHistory.v1` | 易 |
| 監視 / スレ立て通知の条件 | なし（デスクトップは Discord 通知で別の仕組み） | `watchList.v1` の `watched`、`settings.v1` の `threadAlerts` | 対象外 |
| 認証（BE / UPLIFT / どんぐり） | `auth_config.json` | セキュアストレージ | **同期しない（決定済み）** |
| スレ本文のキャッシュ / AI モデル | `cache.db` / `models/` | SQLite / ファイル | 同期しない |

**書き込み履歴の注:** モバイルの履歴にはレス番号が無い。デスクトップは受け取った履歴のレス番号を、
モバイルと同じ照合（本文と時刻）で求める必要がある。照合はスレを開いたときに行い、見つからなければ
番号なしのまま持つ。デスクトップからモバイルへは、番号を付けたまま渡せば足りる（モバイルは照合で求め直す）。

### 3-3. 設定のうち、両方にあって意味が同じもの

設定の大半（テーマ、文字サイズ、レイアウト、ジェスチャーなど）は端末ごとに最適な値が違うので、同期しても
嬉しくない。両方にあって意味が同じなのは、主に NG と書き込みの動作設定。

| 意味 | デスクトップ（localStorage） | モバイル（`settings.v1`） | 値の違い |
|---|---|---|---|
| ID の NG の期限（日） | `desktop.ngIdExpireDays.v1` | `ngIdExpireDays` | — |
| ID の強調の期限（日） | `desktop.hlIdExpireDays.v1` | `highlightIdExpireDays` | — |
| 連投 ID の自動 NG（件数 / モード） | `desktop.ngIdPostCount.v1` / `ngIdPostCountMode.v1` | `ngAutoIdCount` / `ngAutoIdMode` | — |
| 同じ本文の連投 | `desktop.ngDupBodyMode.v1`（無効は `""`） | `ngDupBodyMode`（無効は `'off'`） | **無効の表し方が違う** |
| NG への返信も隠す（有無 / モード） | `desktop.ngChainReplies.v1` / `ngChainRepliesMode.v1` | `ngChainReplies` / `ngChainRepliesMode` | — |
| NG ワードをスレタイにも使う | `desktop.ngWordsInThreadList.v1` | `ngWordsInThreadTitle` | — |
| 書き込み履歴を残す | `desktop.myPostRecordDisabled.v1` | `keepPostHistory` | **真偽が逆** |

名前から対応を取った。値の型と既定値は実装のときに 1 つずつ確かめること。

### 3-4. スレの識別子が違う

- デスクトップ: 板の URL とスレのキーの組（`https://nova.5ch.io/livegalileo/` + `1234567890`）
- モバイル: `host/board/key` の文字列（`nova.5ch.io/livegalileo/1234567890`。`src/lib/urls.js` の `threadId()`）

どちらもホスト名を含むので、**板がサーバーを移ると同じスレが別物に見える。** 同期の形式では
ホスト名を外した `サイト:板/キー`（例: `5ch.io:livegalileo/1234567890`）を識別子にする。
サイトを入れるのは、kenmo.org などの互換サイト（デスクトップ `kenmoEnabled`、モバイル `compatSites`）と
5ch.io の板名が重なっても混ざらないようにするため。変換は既存の `normalize_5ch_url()` /
`parseBoardLocation()` を通す。

## 4. 同期する範囲（決定、2026-11-14）

ユーザーが決めた範囲。

| 対象 | 備考 |
|---|---|
| お気に入り | スレと板の両方（決定） |
| 既読 | 何番まで読んだか |
| ここまで読んだ | 利用者が付ける印 |
| NG | ワード / 名前 / スレタイ。**ID の NG は同期しない**（決定。ID は日付で変わり、量の大半を占める） |
| 強調表示 | |
| 曖昧 NG のルール | ルールの定義だけ。判定の結果は端末ごと |
| NG の動作設定 | §3-3 の項目 |
| 最近開いたスレ | 件数の上限は端末ごと（モバイル 100） |
| 書き込み履歴 | §3-2 の注（レス番号の扱い） |
| 画像のアップロード履歴 | 両方とも最大 20 件 |
| 読んでいた位置 | レス番号。モバイルは最大 300 件 |

**しないもの:** 認証、テーマ・文字サイズ・レイアウト、タブ構成、スレ本文、AI モデル、通知の設定、
名前・検索の履歴、画像 NG（§2 の決定と §9-7「同期しないもの」。名前・検索の履歴と画像 NG は今回の対象に入っていない）。

**件数に上限があるもの**（最近開いたスレ、書き込み履歴、アップロード履歴、読んでいた位置）は、
全端末の分を合わせてから各端末が自分の上限で切る。上限から溢れて落ちた分は「削除」として扱わない。
利用者が自分で消したもの（「履歴から削除」など）だけを削除の記録に残す。

公開の順番は、形の近いものから: お気に入り・既読・ここまで読んだ → NG・強調表示・曖昧 NG・動作設定 →
最近開いたスレ・読んでいた位置・アップロード履歴 → 書き込み履歴。**1 回のリリースに全部を入れるか、
分けるかは未定。**

## 5. 共通部分: 交換の形式とマージの規則

運び方（§6）に関係なく要る。ここを先に作れば、運び方は後から差し替えられる。

### 5-1. 形式

データの種類ごとに 1 つの JSON 文書にする（`favorites` / `read` / `ng` / `highlights` / `prefs`）。
種類ごとに分けるのは、既読は頻繁に変わり NG はほとんど変わらないので、変わったものだけ送るため。

```jsonc
// 例: read（既読とここまで読んだ）
{
  "schema": 1,
  "items": {
    "5ch.io:livegalileo/1234567890": {
      "read": 512,                      // 既読。大きいほうを採る
      "marker": { "no": 480, "at": 1794000000000 },  // ここまで読んだ。新しいほうを採る
      "markerDeletedAt": null,          // 解除した時刻（解除を伝えるため）
      "at": 1794000000000               // この行を最後に触った時刻（古い行を落とすため）
    }
  }
}
```

- `schema` が自分の知らない番号なら、**読まずに中止する**（古い版が新しい形式を壊さないため）。
- スレのタイトルと板の URL は、お気に入りと最近開いたスレには要る。既読には入れない（量が増える）。

### 5-2. マージの規則

両方の端末が、相手の文書と自分のデータを同じ規則で混ぜる。規則は順番に関係なく同じ結果になるものにする。

| データ | 規則 |
|---|---|
| 既読 | 大きいほう。デスクトップの「前進のみ」と同じ考え方 |
| ここまで読んだ | 時刻が新しいほう。解除も時刻で比べる |
| お気に入り（スレ / 板） | 項目ごとに、追加と削除の時刻が新しいほう |
| NG / 強調表示 | 項目ごと（種類 + 値）に、追加・変更・削除の時刻が新しいほう |
| 動作設定 | 設定ごとに、変えた時刻が新しいほう |

### 5-3. いまのデータに足りないもの

マージに要るが、いまの保存形式に無いもの。**ここが実装の一番大きな部分。**

1. **削除の記録。** どちらのアプリも、お気に入りや NG を消すと行ごと消える。このままだと、片方で消した
   お気に入りが次の同期で相手から戻ってくる。消した時刻を残す仕組み（例: 90 日で捨てる削除の控え）が要る。
2. **時刻。** デスクトップの `read_marker.json` とお気に入りには時刻が無い。初回の同期では時刻 0 として扱い、
   以後の変更から時刻を付ける。
3. **並び順。** お気に入りは、デスクトップが手動の順、モバイルが新しい順（手動 / 新着を上の切り替えあり）。
   順番まで同期するかは決めが要る（§9）。勧めるのは「中身だけ同期して、順番は端末ごと」。
4. **既読の解除。** デスクトップはキャッシュを消すと既読も消す（`clearReadStatus`）。「大きいほう」の規則だけだと
   相手から戻ってくる。解除の時刻を持たせる。

### 5-4. 守ること（既存の不変条件）

- **既読とお気に入りを壊さない**（モバイルの不変条件 5）。マージの結果を書く前に、いまのデータを控えに取る。
  マージ後の件数が極端に減っていたら書かずに中止する。
- **既読位置を勝手に変えない**（モバイルの不変条件 3）。同期で既読が進むのは「相手の端末で読んだ」場合だけ。
- デスクトップの `read_status.json` は load → 変更 → save を直列のキュー（`readStatusQueueRef`）で書いている。
  同期の書き込みも**同じキューに載せる。** 別経路で書くと、開いているタブの既読が巻き戻る。
- 開いているスレの画面は、同期で既読が変わっても表示中の位置を動かさない。

### 5-5. テスト

マージは純粋な関数にして、両アプリで同じ入力と期待値の表（JSON の fixture）を通す。
モバイルは jest、デスクトップは Rust 側に置くなら `cargo test`、TypeScript 側に置くなら smoke とは別に
node で回せる形にする。**両方の実装が同じ結果を返すこと**を fixture で保証する。

## 6. 運び方の比較

| | 方式 | 自動 | 双方向 | iOS | Android | サーバーの運用 | 新しい依存 | 判断 |
|---|---|---|---|---|---|---|---|---|
| **A** | ファイルの書き出し / 読み込み（共有シート、ファイル選択） | × | 手動で両方向 | ○ | ○ | なし | なし | 2026-11-11 現実的でない |
| **B** | クラウドの同期フォルダに置いた交換ファイル（OS のファイル選択を通す） | Android ○ / iOS × | ○ | 毎回選ぶ | ○ | なし | なし | 次点 |
| **C** | 端末で暗号化して中継サーバーに置く | ○ | ○ | ○ | ○ | あり | モバイルに 1 つ | **2026-11-14 却下** |
| **D** | LAN 直接（同じ Wi-Fi で直送） | 家にいるときだけ | ○ | ○ | ○ | なし | デスクトップに HTTP サーバー | 現実的でない |
| **E** | QR | × | デスクトップ → モバイルのみ | ○ | ○ | なし | 両方に 1 つずつ | 保留 / 実装しない |
| **F** | **利用者自身の Google ドライブを API で使う** | ○ | ○ | ○ | ○ | なし | モバイルに 1 つ | **ユーザーの希望（2026-11-14）。§7** |

### B について調べたこと

デスクトップに「パソコン版 Google ドライブ」などを入れ、モバイルは OS のファイル選択でそのフォルダを開く方式。

- モバイルに入っている `expo-file-system` には、フォルダを選ぶ `Directory.pickDirectoryAsync` と
  ファイルを選ぶ `File.pickFileAsync` がある（`node_modules/expo-file-system` で確認）。
- **Android** は選んだフォルダの権限を持ち続ける（`takePersistableUriPermission` を呼んでいる）。
  一度選べば、以後は自動で読み書きできる見込み。
- **iOS** はアクセス権を保存する処理（security-scoped bookmark）が**ネイティブ側に無い。**
  アプリを開き直すたびに、利用者がフォルダかファイルを選び直す必要がある。
- 利用者が両方の端末に同じクラウドストレージのアプリを入れている必要がある。Google ドライブは
  フォルダの選択に対応していないという話があり、**提供元ごとの動きは実機で確かめていない。**

iOS で自動にならないので、F を勧める。F はクラウドストレージのアプリを入れていなくても動く。

### D / E を勧めない理由

- **D**: 家の Wi-Fi にいるときしか動かない。Windows のファイアウォールの確認、iOS のローカルネットワークの
  許可が要る。
- **E**: 一方向で、量に上限がない（§9-7 で結論済み）。

## 7. 勧める方式（F）: 利用者自身の Google ドライブ

### 7-1. 考え方

- 利用者が各端末で自分の Google アカウントにログインし、Ember に「Ember 用の領域だけ」を使う許可を出す。
- データは**利用者自身の Google ドライブ**に置く。開発者のサーバーは通らず、開発者は中身を見られない。
  運用するサーバーが無いので、費用も障害対応も無い。
- 既定はオフ。利用者が設定で「Google ドライブで同期」を始めたときだけ動く。
- アカウントは同期のためだけに使う。Ember 自体のアカウント登録は作らない。

### 7-2. 置き場と権限

| 項目 | 内容 | 確認 |
|---|---|---|
| 権限（スコープ） | `drive.appdata`。アプリ専用の隠し領域（`appDataFolder`）だけを読み書きする。利用者のほかのファイルには触れない | 公式の資料で「non-sensitive」と確認した |
| 領域の性質 | ドライブの画面には出ない。利用者は「アプリの管理」から消せる。共有もゴミ箱への移動もできない | 公式の資料で確認した |
| 3 つのアプリで同じ領域が見えるか | Windows / Mac / iOS / Android は OAuth のクライアントが別になる。**同じ Google Cloud のプロジェクトに置けば同じ領域を共有できる見込みだが、公式の資料では確かめられなかった** | **未確認。最初に実機で確かめる（§10）** |
| 代わりの権限 | 上が共有できなければ `drive.file`（アプリが作ったファイルだけ。ドライブの画面に見える）。これも non-sensitive | 同じ点の確認が要る |

`appDataFolder` を勧める理由は 2 つ。利用者が誤ってファイルを動かしたり消したりしない。同意の画面に出る
権限の説明が「アプリ自身の設定データ」だけで済む。

### 7-3. 端末ごとのファイル（ぶつからない書き方）

Google ドライブには「自分が見た版と同じときだけ上書きする」確実な手段が無い。そこで、**各端末は自分の
ファイルだけを書き、ほかの端末のファイルは読むだけ**にする。

```
appDataFolder/
  devices.json                 … 端末の一覧（ID、名前、最後に同期した時刻）
  <端末ID>.favorites.json
  <端末ID>.read.json
  <端末ID>.ng.json
  <端末ID>.prefs.json
```

- 同期のたびに: ほかの端末のファイルのうち変わったものを取る → 自分のデータとマージする（§5-2） →
  自分のファイルを書き直す。
- 書き込みがぶつからないので、同時に動いても壊れない。マージは順番に関係なく同じ結果になる規則なので、
  何度か回るうちに全端末が同じ内容になる。
- 変わったかどうかは、ファイルの一覧（更新時刻か版の番号）だけを先に取って判断する。変更が無ければ
  1 回の通信で終わる。
- 長く同期していない端末（例: 180 日）のファイルは一覧から外して消す。
- `devices.json` だけは全端末が書くが、失っても作り直せる情報しか入れない。

### 7-4. ログイン（OAuth）

| | 方法 | 新しい依存 | 確認 |
|---|---|---|---|
| **デスクトップ** | 既定のブラウザで Google の同意画面を開き、`http://127.0.0.1:<空きポート>` で結果を受ける。クライアントの種類は「デスクトップアプリ」 | **なしで書ける見込み。** 受け口は `std::net::TcpListener`、通信は既存の `reqwest`（30 秒のタイムアウトを付ける） | デスクトップではこの受け方が今もサポートされていると公式の資料で確認した |
| **iOS** | 同意画面をアプリ内ブラウザで開き、専用の URL スキームで結果を受ける | 下の 2 案のどちらか | 公式の資料に載っている方法 |
| **Android** | Google の公式 SDK を通すのが推奨。URL スキームで受ける方法は、新しいクライアントでは既定で無効になっているという話がある | 下の 2 案のどちらか | **未確認** |

モバイルの依存は次のどちらか。**どちらもネイティブの依存で、ユーザーの承認が要る。**

1. **`@react-native-google-signin/google-signin`**: Google の公式 SDK を包んだもの。iOS と Android の
   両方で推奨の経路を通る。権限の追加とアクセストークンの取得（`getTokens`）ができる。
   無料で使える範囲がどこまでかは確かめられなかった。
2. **`expo-auth-session` + `expo-crypto`**: Expo 公式。iOS は問題ない見込み。Android は上の
   「URL スキームが既定で無効」に当たる可能性がある。

**1 に決めた。** Google の資料に「Custom URI schemes are no longer supported on Android」とあり、
2 は Android で使えない（2026-11-14 に確認）。無料の「Original」の API を使う。

ほかに決めること:

- **トークンの置き場。** モバイルはセキュアストレージ（`expo-secure-store`、導入済み）。デスクトップは
  **データフォルダ（同期フォルダへ向けられる）には置かない。** `location.json` と同じく端末ごとの場所に置く。
  トークンは Cookie と同じ扱いにして、ログに出さない。
- **デスクトップのクライアントの「シークレット」。** デスクトップアプリの種類ではバイナリに埋め込む前提で、
  Google も秘密として扱わないとしている。それでもリポジトリに平文で置くかは決めが要る。
- **ログインの切れ。** 利用者が Google 側で許可を取り消したら、同期を止めて「もう一度ログイン」を出す。
  アプリのほかの動きは止めない。

### 7-5. Google 側の手続き

- Google Cloud にプロジェクトを 1 つ作り、Drive API を有効にする。クライアントを 3 種類
  （デスクトップ / iOS / Android）作る。Android は署名の指紋（Play の署名と開発用）を登録する。
- 同意画面を「本番」にする。アプリ名、ホームページ、プライバシーポリシーの URL が要る。ホームページの
  ドメイン（`ember-5ch.pages.dev`）の所有を Search Console で示す必要があるかもしれない。
- `drive.appdata` は non-sensitive なので、重い審査（制限付きスコープの審査）は要らない。
  **基本の確認（ブランドの確認）が要るか、未確認のまま使える人数に上限があるかは確かめられなかった。**
- Google の API の利用規約（利用者データの方針）に沿って、プライバシーポリシーに「Google ドライブの
  アプリ専用領域に、同期のデータだけを置く。ほかの用途には使わない」と書く。
- Drive API は無料で、回数の上限は同期の用途には十分大きい。

### 7-6. 同期のタイミング

- モバイル: アプリを前面に出したとき、スレを閉じて少し経ったとき、背面へ回るとき。
- デスクトップ: 起動時、変更から 30〜60 秒後（まとめて送る）、数分おき、終了時。
- 通信に失敗しても、アプリの動きは止めない。次の機会にやり直す。
- モバイル回線では既読だけにするなどの絞り込みは、量を測ってから決める（既読 300 スレで数十 KB の見込み）。

### 7-7. ストアとプライバシーの文面

いまのストアの説明とプライバシーポリシーは「閲覧履歴、お気に入り、NG などは端末の中に保存します」と
書いている（`docs/STORE_METADATA.md`）。同期を入れるなら書き足しが要る。

- 「同期をオンにすると、利用者自身の Google ドライブに保存します。開発者には送りません」という趣旨
- 説明文、App のプライバシー、データセーフティ、`apps/landing` の `privacy.html`
- 利用者が自分のドライブへ送るデータを「収集」と申告するかは、**両ストアの最新の定義を確かめてから決める。**
- iOS で Google ログインを入れると「Apple でサインイン」も求められる規定がある。Ember のログインではなく
  Google ドライブへの接続なので当たらない見込みだが、**審査の前に確かめる。**

### 7-8. Google ドライブ以外

「運び方」は、ファイルの一覧・取得・書き込みの 3 つの操作だけに絞った部品にする。そうしておけば、
Dropbox や OneDrive を後から足すときに、マージや画面を作り直さずに済む。**初版は Google ドライブだけ**を勧める。
同時に複数を作ると、ログインの手続きと審査が提供元の数だけ増える。

iCloud は Windows のデスクトップ版から API で使えないので、対象にしない。

## 付録: 却下した中継サーバー方式（C）

端末で暗号化したデータを Cloudflare Workers に置く方式。2026-11-14 に検討し、ユーザーが却下した。
**再提案しない。** 残すのは、同じ検討を繰り返さないための要点だけ。

- 利点: 全 OS で自動・双方向。Google アカウントが要らない。
- 欠点: サーバーの運用と費用が要る（無料枠は Workers のリクエストが 1 日 10 万で、ほかのプロジェクトと共有）。
  モバイルに暗号の依存が要る。ストアの文面の書き直しが大きい。
