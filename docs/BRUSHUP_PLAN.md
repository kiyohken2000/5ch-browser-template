### [T1] CI にテスト・Lint を追加 — ステータス: ✅ 完了 (2026-07-08)。rust-check-linux ジョブに clippy / test ステップを追加。ローカルで両方 green を確認済み (clippy 警告 0、テスト 49 件 pass)

**目的**: 現在の CI (`.github/workflows/ci.yml`) は `cargo check` + フロントビルド + smoke UI のみで、`cargo test` / `cargo clippy` が走っていない。リグレッションを CI で検知できるようにする。

**現状**: ワークスペースに Rust テストが約 50 件あるが CI では実行されていない。clippy はローカルの `/lint` スキル頼み。

**変更内容**:
1. `rust-check-linux` ジョブに以下のステップを追加(Windows ジョブは Vulkan ビルドが重いので追加しない):
   - `cargo test --workspace` (`--ignored` は付けない — ネットワークテストは除外)
   - `cargo clippy --workspace -- -D warnings`
2. clippy が現状のコードで警告を出す場合は、このタスク内で警告を解消する(`#[allow]` の乱用はしない)。

**対象ファイル**: `.github/workflows/ci.yml`、警告解消のため各 crate の `lib.rs`

**完了条件**: CI が green。ローカルで `cargo test --workspace` と `cargo clippy --workspace -- -D warnings` が通ること。

### [T3] src-tauri lib.rs のモジュール分割 — ステータス: ❌ 却下 (2026-07-07)

**目的**: `apps/desktop/src-tauri/src/lib.rs` が 2,602 行・Tauri コマンド 75 個で、「2000 行超まで分割しない」ルールの分割条件を満たしている。機能ドメインごとのモジュールに分割し見通しを改善する。

**変更内容**:
1. 以下のようなドメイン別モジュールに分割する(実際の関数配置を見て調整可):
   - `src/commands/ai.rs` — `ai_*` コマンド群(モデル管理・推論)
   - `src/commands/fetch.rs` — 板・スレ・レス取得系
   - `src/commands/post.rs` — 投稿・スレ立て系
   - `src/commands/store.rs` — お気に入り / NG / 既読 / 設定の永続化系
   - `src/commands/auth.rs` — ログイン系
   - `lib.rs` — `run()`、`generate_handler![]`、共通 state 定義のみ残す
2. **挙動を一切変えない純粋なリファクタリング**とする。コマンド名・シグネチャ・返却型は不変。
3. `generate_handler![]` のコマンド列挙は漏れなく維持(コンパイルエラーで検知できるが、`invoke` 側から呼べなくなる漏れに注意)。
4. `LOGIN_COOKIES` 等の static / Mutex の所在と poison 復旧 (`into_inner()`) の扱いを維持。

**対象ファイル**: `apps/desktop/src-tauri/src/lib.rs` → `src/commands/*.rs` 新設

**完了条件**: `cargo check --workspace` / `cargo test --workspace` が通り、`npx tauri dev` で主要フロー(板一覧 → スレ一覧 → レス表示 → 書き込みダイアログ表示)が動作する。git diff が移動のみであることを確認。完了後 `CLAUDE.md` のリポジトリ構成説明を更新。

8. セッション内の送信結果 (OK/NG) は同じパネルの「今回の送信結果」として残した。

## アイディア(2026-09-21。着手前にユーザー確認必須)

### [N23] 曖昧 NG(自然文ルールによる AI 判定 NG) — ステータス: ✅ 採用 / 未着手(2026-09-27 承認。ゼロショット NLI 分類器 + 述語 AND + 閾値 0.8。実装計画は本節末尾。2026-09-21〜09-26 は生成 LLM / reranker / Laya で見送っていた経緯を下に残す)

**背景**: 現在の NG は「ワード / ID / 名前 / スレタイ」の文字列一致(正規表現含む)のみ。「政治ネタで煽っているレス」「特定の話題を延々と繰り返す人」のような、文字列では書けない条件を NG にしたいという発想。きっかけは TypeSafe AI の判定特化モデル Jev(2026-09-15 発表、分類・採点結果を確率つきで返す)の記事だが、**Jev は不採用**(下記)。

**Jev 不採用の理由(2026-09-21 判定。再提案しないこと)**:
- クラウド API のみ(`POST https://api.typesafe.ai/v1/systemone`)で、重みの配布・ローカル実行がない。NG 判定は閲覧した全レス本文を送ることになり、AI_INTEGRATION_PLAN の「すべてローカル完結・外部送信なし」方針と衝突する
- ユーザー各自に API キーを設定させる必要がある(開発者キーの埋め込みは抜き取り・課金リスク)
- 日本語対応が明記されていない("Text only" のみ)。5ch のレスで精度が出るか未検証
- 料金($0.042 / 100万入力トークン)・レイテンシ(70〜500ms)自体は問題にならない

**やるなら: 既存のローカル LLM で実現する案**:
1. NG パネルに「AI NG ルール」を追加。ルールは自然文(例: 「政治の話題で他人を罵倒している」)。既存の NG エントリと同じく有効 / 無効・モード(非表示 / あぼーん)を持つ
2. 判定は `ai_run_inference` 系の推論基盤(core-ai / llama-cpp-2)を使い、「このレスはルールに該当するか」を **yes / no の 1 トークンだけ**生成させる。生成コストはほぼゼロで、logit から確率が取れるので、閾値(既定 0.8 程度)未満は「未判定」として通常表示する
3. **速度が最大の課題**(1000 レスを 1 件ずつ判定するとプロンプト処理だけで GPU で数十秒〜数分、CPU はさらに遅い)。そのため同期判定はせず、**遅延 NG** にする:
   - 対象は新着レスのみ。スレを開いた / 更新した後に裏で順次判定する
   - 結果は SQLite キャッシュにレス ID(スレ URL + レス番号)+ ルール ID ごと保存し、次の描画から `ngResultMap`(App.tsx の 1 パス目)に差し込む。判定中のレスは通常表示のまま
   - ルール文を編集したらそのルールのキャッシュを破棄して再判定
   - モデル未有効時は機能を出さない(既存の AI 機能ゲーティングに従う)
4. 既存の連鎖(ID 連鎖・連鎖あぼーん)には乗せない(誤判定が波及するため)。まずは単発レスの判定のみ
5. 精度検証: 実スレで数ルールを試し、誤判定率が実用に耐えなければ見送る。1B〜2B クラスのモデルでは日本語の皮肉・文脈依存の判定は弱い可能性が高い

**代替候補: Laya(Jev クローンの公開実装。2026-09-21 追記、未検証)**:
- Jev と同じ「選択肢にスコアを付けるだけ」の判定特化モデルの公開実装。ModernBERT(421M)/ mmBERT(322M、多言語)ベースで、質問タイプは `choice` / `score` / `noul`(yes/no)。重みは Hugging Face で配布(`aac6fef/laya-multilingual-mlx` など)、fp16 で 647MB(うち 61% が 256k 語彙の embedding)
- Jev 不採用理由のうち「クラウド API のみ」「API キー必須」は該当しない(ローカル実行可・多言語版あり)。日本語精度は同じく未検証
- 速度の参考値(mizchi 氏の記事 https://zenn.dev/mizchi/articles/laya-mlx-60fps): Apple Silicon の MLX で 1 判定 8ms(約 90 判定/秒)、WebGPU fp16 で約 20 判定/秒、WASM で約 5 判定/秒。上記 3 の「速度が最大の課題」は、生成 LLM の yes/no 判定より大幅に軽くなる可能性がある
- **課題**: Ember の推論基盤は llama.cpp(GGUF)で、Laya は BERT 系エンコーダ。llama.cpp の BERT 対応で GGUF 化して分類ヘッドまで動かせるかは未確認。動かない場合は別の推論ランタイム(ONNX Runtime など)を追加することになり、新規 crate の承認が必要
- MLX 移植の本体: https://github.com/mizorewww/laya-mlx(Apache-2.0、2026-09-19 公開、2026-09-22 確認)。上記 zenn 記事はこの実装の測定。README の公称値は M3 Max・FP16 で短い質問 1 件 P50 13.4 ms(英語 421M)/ 7.4 ms(多言語 322M)、ピークメモリ 940 / 690 MiB、上流 PyTorch 版と 63/63 問で選択ラベル一致。**Apple Silicon + Python 3.11+ + macOS 14+ 限定**の Python パッケージなので、Rust/Tauri の Ember からそのまま使えず Windows では動かない。採用するなら上記「課題」の別ランタイム問題は変わらず
- **(2026-09-27 追記)** クロスプラットフォームの実行基盤 **ollaya**(Rust、ONNX Runtime)が公開され、上記の「Apple Silicon 限定」は解消した。ただし日本語版(`laya:multilingual`)は zero-shot の型付き判定がほぼ偶然(0.362)で、Laya そのものは本節の用途には現時点では使えない。評価の詳細は下記「別方式の検証: ollaya」。**ただしこの調査から別のモデル(ゼロショット NLI 分類器)に行き着き、そちらは実測で成立した** — 下記「別方式の検証: ゼロショット NLI 分類器」を先に読むこと
- 判断の質が「ルール文(説明文)の書き方」に強く依存する点は Jev と共通。ユーザーが書く自然文ルールでそのまま精度が出るかは要検証

**同方式の実証例: SemIf(旧 OpenJev。2026-09-21 追記)**: https://openjev.com — TypeSafe とは無関係の独立研究プロジェクト。汎用 GGUF モデル(Qwen3 0.6B / MiniCPM5 2B / Qwen3.5 4B)を wllama(llama.cpp の WASM 版)+ WebGPU でブラウザ実行し、「選択肢の logit を直接読む方式」と「JSON を生成させる方式」を同じ質問で比較するデモ。独自評価(英語)の精度は MiniCPM5 2B 68.6%、Qwen3.5 4B 81.3%。専用モデルなしでも上記 2 の「1 トークン判定 + logit 確率」が成立する裏付けになる。Laya と違い **Ember の llama-cpp-2 / GGUF 基盤にそのまま乗る**構成で、Qwen3.5-4B はカタログ収録済み。

**SemIf 方式の要点(openjev.com の worker.js を 2026-09-21 に確認)**:
- chat 形式: system「Make the requested decision from the supplied state. Follow the output format exactly.」+ user「State: … / Question: … / Allowed options: A. … B. … / Reply with exactly one option letter from: A, B」
- `max_tokens: 1`、thinking 無効(`enable_thinking: false`)、grammar でラベル文字のみ許可、ラベルトークンに `logit_bias +100`
- 最初の生成トークンの top_logprobs からラベル(A / B / …)の logit を取り、**ラベルだけで softmax**。サイト自身が「calibrated confidence ではない」と注記
- モデルごとにラベル `A` のトークン ID(`labelBase`: Qwen=32、MiniCPM=54)をハードコードしている
- **llama.rn(React Native の llama.cpp バインディング)で同方式を動かした際の落とし穴(FeedOwn 側で 2026-09-21 実機確認。Ember の llama-cpp-2 には直接関係しないが、生成 API 経由で確率を読む実装全般に当てはまる)**:
  1. `logit_bias` を渡すとネイティブクラッシュ(`cpp/jsi/JSIParams.cpp` が `std::vector<llama_logit_bias>` をトークン ID で添字アクセス。`ignore_eos` も同じ。main でも未修正)。grammar だけで足りるので `logit_bias` 行は削除
  2. `completion_probabilities` が completion をまたいで蓄積する(非並列 `completion()` の `generated_token_probs` が `rewind()` で clear されない)。`[0]` を読むと最初の 1 件の値が全件に出る → **末尾要素を読む**
  3. `n_probs` はサンプラ適用後の値。llama.cpp 既定の `min_p 0.05 / top_k 40 / top_p 0.95` が掛かったままだと弱い側のラベルが切り捨てられて 0 になる → `temperature 1, top_k 0, top_p 1, min_p 0, typical_p 1` を明示する。grammar 有無での確率差はごく小さい(Qwen3 0.6B で 0.920 / 0.916)
  - 1 と 2 は llama.rn の Issue として報告済み(post-sampling probs の提案つき): https://github.com/mybigday/llama.rn/issues/401
  - Ember の `scripts/probe_ng_llm.rs` は `ctx.get_logits()` の生 logits から A / B の 2 値 softmax を自前計算しており、サンプラチェーンを通らないので 3 の切り捨ては受けない(2026-09-21 確認)

**SemIf 方式で N23 を実装する場合の検討(2026-09-21。未着手・採否未定)**:
1. **core-ai に判定 API を追加**: `score_options(model_path, prompt, option_labels, backend, cancel) -> Vec<f32>`。`complete_streaming` のプロンプト処理部(モデルキャッシュ・コンテキスト生成・チャンク decode)を流用し、生成ループの代わりに最後の decode 後の `ctx.token_data_array()` から各ラベルトークンの logit を読んで softmax を返す。生成トークンは 0。ラベルトークン ID はハードコードせず `model.str_to_token("A", AddBos::Never)` で引き、1 トークンにならないモデル(要確認: gemma / lfm2 / gemma4)は未対応として弾く
2. **プロンプト**: 既存の `aiWrapTurn` / `aiSystemTurn` / `aiOpenAssistantTurn`(qwen は `<think>\n\n</think>` プリフィル込み)を流用し、NG は 2 択(A: ルールに該当する / B: 該当しない)の noul 相当にする。閾値は P(A) ≥ 0.8 既定、NG パネルで調整可。grammar / logit_bias は不要(logit を直接読むだけなので生成しない)
3. **速度**: `complete_streaming` はコールごとに n_ctx 8192 のコンテキストを作るため、レス 1 件ずつ呼ぶとコンテキスト生成がボトルネックになる。判定用 API はコンテキストを使い回し、共通プレフィックス(system + ルール文)を KV キャッシュして**レス本文だけ decode → logit 読み → プレフィックス位置まで KV を巻き戻す**構造にする。レス 1 件のプロンプトは 200〜400 トークン程度なので、GPU で数十 ms、CPU で数百 ms〜秒のオーダーと見込む(要実測)。複数ルールはルールごとにレスをまとめて回す
4. **排他**: 推論は `model_cache` の Mutex で直列化され、`ai_inference_cancel` はスロット 1 つ。判定は要約 / 返信生成 / 翻訳が動いていない**アイドル時のみ**バックグラウンドで進め、ユーザー操作の推論が来たら判定を中断して譲る
5. **精度**: SemIf の数値は英語タスク。日本語の 5ch レスで Qwen3.5-4B(カタログ収録済み)/ LFM2.5-1.2B-JP を数ルールで実測してから採否を決める。ラベル softmax は calibrated ではないので、閾値はデータを見て決める
6. 遅延 NG・SQLite キャッシュ・連鎖に乗せない・モデル未有効時は UI に出さない、は上記 3〜4 のまま

**未確認事項の調査結果(2026-09-21。検証プローブ `scripts/probe_ng_llm.rs`(examples/ にコピーしてビルド)、Gemma4-E2B-IT Q4_K_M、Windows / 32 スレッド CPU / Radeon RX 550)**:
- **logit 読み出し API**: `LlamaContext::get_logits() -> &[f32]`(n_vocab 長、最後に `logits=true` で decode したトークン分)をトークン ID で添字するだけ。`candidates()` / `token_data_array()` は同じ配列を `LlamaTokenData`(`.id()` / `.logit()`)に包んだもの。`get_logits_ith(i)` でバッチ内の任意位置も取れる
- **KV 巻き戻し API**: `LlamaContext::clear_kv_cache_seq(Some(0), Some(prefix_len), None)`(内部は `llama_memory_seq_rm`)。プレフィックス直後まで巻き戻して次のレス本文を同じ位置から decode できることを確認
- **ラベルの単一トークン性(Gemma4 トークナイザ)**: `A` = 236776、`B` = 236799 で各 1 トークン。`<|turn>model\n` 直後に `A` を足しても前段のトークン列は変わらない(プレフィックス一貫性 OK)。`はい` は 1 トークンだが `いいえ` は 2 トークンなので、ラベルは A / B の英字にする。qwen / lfm2 / gemma3 は未計測(モデル未インストール)
- **精度(日本語・手書き 12 件、ルール「政治の話題で他人を罵倒している」)**: 11 / 12 正解。唯一の誤りは「お前みたいなバカがいるからスレが荒れるんだよ。消えろ」(政治要素なしの罵倒)を P(A)=1.000 で該当と判定 — ルールの複合条件(政治 **かつ** 罵倒)の片側だけで反応する傾向。P(A) はほぼ 0.000 / 1.000 に飽和しており、**閾値 0.8 は不確実性フィルタとして機能しない**(SemIf の「calibrated ではない」注記どおり)。全 12 件で最上位トークンは A か B(思考チャネルへの逸脱なし)
- **速度**: CPU で「レスごとに新規コンテキスト」約 700ms / 件(約 105 トークン)、「プレフィックス KV 共有 + 巻き戻し」約 400ms / 件(本文 + 末尾 約 60 トークン)。GPU(RX 550)は逆に遅く 2.3 秒 / 1.45 秒 — このカードが弱いだけの可能性が高く、他 GPU では未計測。実装するなら CPU 前提で 1 スレ 100 レスの新着 = 40 秒〜70 秒のバックグラウンド処理になる
- **LFM2.5-1.2B-JP Q4_K_M(同日追試、CPU)**: **不適**。12 件中 5〜6 件正解(偶然と同等)で、ほぼ全レスを「該当する」と答える。選択肢の意味を A / B 入れ替えても「該当する」側を選ぶので位置バイアスではなく意味的な yes バイアス。指示文を system ターンに出すと 6〜8 / 12 に上がるが不安定。速度は約 380ms / 件(トークン数は Gemma4 より多い 約 130)
- **KV 巻き戻しはアーキテクチャ依存**: LFM2(Hybrid Conv + Attn)と **Qwen3.5(Gated DeltaNet + Attn)** では `clear_kv_cache_seq` の部分削除が `false` を返す(再帰型メモリは範囲削除不可)。全消去 + プレフィックス再 decode にフォールバックすると新規コンテキストと同等の時間で、プレフィックス共有の効果はゼロ。有効なのは Gemma4 / Gemma3 のような純 Attention モデルのみ。実装するなら戻り値を見てフォールバックする必要があり、プレフィックス共有は「効けば速い」程度の最適化として扱う
- **Qwen3.5-4B Q4_K_M(同日追試、CPU)**: **11 / 12 正解**(誤りは Gemma4 と同じ「政治要素なしの罵倒」1 件)。Gemma4 と違い **確率が飽和せず使える**: 該当 0.97〜0.99、明確な非該当 0.01〜0.24、境界例(「立憲の議員がまた失言してて笑った」「>>12 それ去年のニュースだぞ」)は 0.45〜0.54 に落ちる。選択肢を A / B 入れ替えても同じ判定(位置バイアスなし)。`<think>` はプリフィルで抑止でき最上位は常に A / B。**速度は約 1.6 秒 / 件(CPU)** で Gemma4-E2B の 4 倍
- **結論**: 技術的には既存基盤だけで成立し、追加 crate は不要。モデル依存が大きい: LFM2.5-1.2B-JP は不可、Gemma4-E2B は精度 11/12 で速い(0.4〜0.7 秒 / 件)が確率が 0/1 に飽和して閾値が効かない、Qwen3.5-4B は精度 11/12 で閾値 0.8 が境界例の除外として機能するが 1.6 秒 / 件と遅い。**推奨は「判定はアクティブモデルに従い、閾値 UI は確率が飽和しないモデル(Qwen 系)でのみ意味がある」前提で Gemma4-E2B 以上を対応モデルとする**こと。実スレ 100 件規模での誤判定率は未計測
- **モバイル実測(FeedOwn 側、iPhone 13 mini / A15 / 4 GB、iOS 27、llama.rn 0.12.4、Metal、同じ 12 件。2026-09-21)**: Qwen3.5-4B と Gemma4-E2B は OOM で載らず、使えるのは **Qwen3.5-2B Q4_K_M のみ**。2B は **10 / 12**(該当 0.57〜0.76 / 非該当 0.11〜0.39 / 境界例 0.39)、約 530 ms / 件。誤りは 4B と同じ「政治要素なしの罵倒」を 0.80 で該当としたものと、「首相会見の雑談」が 0.51 で境界超え(閾値 0.55 なら 11 / 12)。4B の「該当 0.97〜0.99」に対し 2B は該当側のマージンが薄く、**デスクトップで 4B を選ぶ判断は妥当**。Qwen3.5-0.8B は 8 / 12 で全件 0.39〜0.61(判別力なし)、対照の Qwen3-0.6B は 5 / 12(yes バイアス)、Gemma3-1B-IT は 4 / 12(0 / 1 飽和 + 逆向き)
- **訂正: llama.rn 0.12.4 には hybrid モデルのプレフィックス再利用が無い**(0.12.7 で追加、release note #367)。上記 530 ms は毎回約 110 トークンを全 prefill した値(`timings.cache_n == prompt_n`)。「llama.rn なら Qwen3.5 でも状態スナップショットでプレフィックス共有が効く」は main 基準の話で、0.12.4 では効かない

**見送り判定(2026-09-21。GPU 前提案の検討を含む)**:

実装は**見送り**(却下ではない。再検討条件は下記)。判断理由:
1. **精度の根拠が手書き 12 件だけ**で、実スレ規模の偽陽性率が未計測。唯一の誤りが偽陽性(複合条件「政治 かつ 罵倒」の片側だけで反応)で、NG は偽陰性より偽陽性の害が大きい(消えたレスは消えたことに気付けない)。ユーザーが書く自然文ルールの多くは AND 条件になるので同じ穴が広く出る
2. **CPU 前提では速度と精度が両立するモデルがない**: Qwen3.5-4B は確率が使えるが 1.6 秒 / 件(新着 100 件 × ルール 3 本で約 8 分)、Gemma4-E2B は 0.4〜0.7 秒 / 件だが確率が 0 / 1 に飽和して閾値 UI が飾りになる。「閾値がモデルによって効いたり効かなかったりする」設定は説明できない
3. **遅延 NG の UX が専ブラとして不自然**: 見えていたレスが後から消える / あぼーんに変わる動作は、読んでいる最中に画面が動くのでもっとも嫌われる挙動
4. **計画がインフラ先行**: SQLite キャッシュ・バックグラウンドスケジューラ・推論の排他 / 中断(上記 3〜4)を積んでから精度検証(上記 5)で見送り判断をする順序になっていて逆。`App.tsx` / `lib.rs` の複雑さを確実に増やす
5. **対象ユーザーが薄い**: AI 有効 + 4B モデル(2.5 GB)DL 済み + 判定待ちを許容する層。既存の文字列 NG で困っていない層が大半

**GPU 搭載環境(GeForce RTX 等)限定の機能にする案の検討**(RX 550 以外の GPU 実測が無いため、RTX / Mac の数値は llama.cpp の一般的なベンチからの推定):

|---|---|---|---|
| Windows 32 スレッド CPU(実測) | — | 1.6 s | 約 8 分 |
| RTX 3060(Vulkan、推定) | 1,500〜2,500 tok/s | 0.1〜0.3 s | 30〜90 s |

- RTX 級なら **Qwen3.5-4B 固定で設計できる**のが利点: 確率が飽和しないので閾値 UI が意味を持ち、Gemma4 の飽和問題を避けられる。ハイブリッドで KV 巻き戻しが効かない問題も、毎回フル decode しても安いので無視できる。VRAM は 4B Q4(2.5 GB)+ 判定用の小さい n_ctx(1024 程度)で 6 GB あれば足りる
- Ember は CUDA ではなく Vulkan なので、CUDA のベンチより 1.5〜2 倍遅い前提で見る
- **Mac は「速い」とは言えない**: Apple Silicon は生成(メモリ帯域)は得意でもプロンプト処理(演算)は dGPU にかなり劣る。M2 無印は Windows の 32 スレッド CPU と同等で対象外、Pro / Max 以上が実用ライン。既存実測(Gemma3-1B 生成: Mac M2 Metal 33 tok/s vs Windows CPU 29 tok/s、AI_INTEGRATION_PLAN)とも整合。M2 の実数は手元で `scripts/probe_ng_llm.rs` を Qwen3.5-4B で回せばすぐ取れる(RTX は手元に無い)
- **ゲーティングは GPU 名ではなく実測スループットで行う**: llama-cpp-2 からデバイス名・実際に GPU に載ったレイヤー数が取れず(AI_INTEGRATION_PLAN の Vulkan 節 6)、`compiledBackend` は静的値、起動時に `ai_list_backend_devices` を通せない制約もある。機能を有効化する時に判定を 1 件試走し、0.5 秒 / 件を超えたら「この環境では実用速度にならない」と表示して有効化させない方式なら、RTX / Apple Silicon Pro / Intel Arc を区別せず、Vulkan が CPU にフォールバックしているケースも自動で弾ける
- GPU 前提にしても上記理由 1(偽陽性率未計測)と 3(遅延 NG の UX)はそのまま残る。3 は「新着 10 件以下なら判定を待ってから描画、それ以上は遅延」の二段構えで日常の自動更新をほぼ同期扱いにできる可能性はある(設計次第)
- 対象を絞ると「4B モデルを DL 済みで GPU を持つ Ember ユーザー」がどれだけいるかは冷静に見る必要がある

**別方式の検証: クロスエンコーダ (reranker) GGUF — 不採用(2026-09-26。検証プローブ `scripts/probe_rerank_ng.rs`、`gpustack/bge-reranker-v2-m3-GGUF` Q4_K_M(438 MB)、Windows / 32 スレッド CPU)**:

きっかけは判定特化モデル `interfaze-ai/lev`(Qwen3.5-4B の LoRA アダプタ、1 forward pass で yes/no・選択肢・スコアを返す)だが、**lev 自体は不採用** — LoRA + CUDA 必須で GGUF が無く、README に "English only" と明記されていて日本語非対応。同じ「生成せず 1 回の forward pass で 1 スコア」を GGUF で成立させる既製品として、クロスエンコーダ (reranker) を検証した。上記「見送り判定」の理由 2(CPU では速度と精度が両立しない)を正面から潰せる可能性があったため。

- **基盤適合性: 追加 crate 不要で完全に動く**。GGUF は arch `bert` / tokenizer `t5`(UGM・XLM-R 語彙 250,002)/ `n_cls_out=1`、分類ヘッド `cls.weight`[1024,1024] `cls.bias` `cls.output.weight`[1024] `cls.output.bias` を同梱(ヘッダは HTTP range リクエストで DL 前に確認)。ヘッドは Q4_K_M でも F32 のまま。同梱 llama.cpp 側は `LLM_ARCH_BERT` + `LLAMA_POOLING_TYPE_RANK` の分岐(CLS → `cls` → tanh → `cls_out`)を持つ。Rust 側も `LlamaContextParams::with_embeddings(true)` / `with_pooling_type(LlamaPoolingType::Rank)` / `LlamaContext::embeddings_seq_ith()`(RANK のとき `float[n_cls_out]` を返す)/ `token_bos` `token_eos` `token_sep` / `clear_kv_cache` が `llama-cpp-2` 0.1.154 に揃っている。プローブは一発でビルドが通り一発で動いた
- **ペア形式**: この GGUF には `tokenizer.ggml.add_sep_token` が無いため、llama.cpp の `format_prompt_rerank` は `<s> q </s> d </s>`(Sep1)を作る。XLM-R 本来のペア形式は `<s> q </s></s> d </s>`(Sep2)。core-ai に直接実装すれば Sep2 を出せるので両方試したが、下記の結果は変わらなかった
- **実装が正しいことの裏取り**: 本来の検索用途では「日本の首都はどこですか」× 正答文書 = raw +7.778(sigmoid 0.9996)、× 無関係文書 = -11.015(0.0000)、英語ペア +9.672。日本語でもきれいに正負が割れるので、以下の否定的な結果は実装バグではなく**タスクの型の違い**
- **NG 判定としては機能しない**。ルール「政治の話題で他人を罵倒している」をクエリ、レス本文を文書にして `probe_ng_llm.rs` と同じ 12 件を回すと、Sep1 / Sep2 × クエリ言い回し 3 種のすべてで **7/12**。これは「全件を非該当と答えた」だけの数字(非該当が 7 件)。該当レスの raw は -9.2〜-10.9、非該当も -10.2〜-11.0 で、**閾値どころか順位でも一切分離しない**。最高スコアが付いたのは「お前みたいなバカがいるからスレが荒れるんだよ。消えろ」= 政治要素のない罵倒で、**方式 A(SemIf)が唯一間違えたのと同じケース**。複合条件の片側だけに反応する点は共通、しかもこちらは判別力が無い
- **話題(トピック)単独のクエリなら順位は分離する**(ROC-AUC、14 件): 「政治」0.896 /「政治の話題」**0.917** /「選挙や政党についての話」0.646 /「ゲームの話題」0.375(= 非政治側を正しく上位)/「食べ物の話題」0.146(同上)。ただし **絶対スコアが使えない**: 最良でも sigmoid 0.005 で全件が負側に張り付き(下限 -11.01 に飽和)、NG が必要とする「このレス単体が該当か」の絶対判断が成立しない。またルール文が長くなると急に劣化する(0.917 → 0.646)— reranker は短いクエリで訓練されており、ユーザーが書く自然文ルールとは相性が逆。誤りの実例として「>>12 それ去年のニュースだぞ。**ソース**確認してから書けよ」が「ゲームの話題」でも「食べ物の話題」でも上位に来る(ソース = sauce)
- **速度は圧勝**: 約 30 ms / 件(CPU)。方式 A の Qwen3.5-4B が 1.6 秒 / 件なので **53 倍**で、新着 100 件 × ルール 3 本が 8 分 → 9 秒。モデルロード 0.58 秒。ただし判定が出ない以上、速度は意味を持たない
- **結論**: N23 の判定器としては**不採用**。精度不足ではなく、reranker が出すのは「クエリに対する文書の検索関連度」であって「この文がこの述語を満たすか」ではないという原理的な不一致で、チューニングで埋まる差ではない。5ch のレスは「政治の話題で他人を罵倒している」という問いへの答えではないので、構造上どれも正側に来ない
- **副産物(N23 とは別の話)**: 30 ms / 件で話題の AUC 0.9 が取れるのは、並べ替え・絞り込み系の機能(スレ内の意味検索、関連レス抽出、スレの話題から外れたレスの提示)には十分な性能。NG のような絶対判断ではなく相対順位を使う用途なら素直に乗る。**この線は [N24] で追って調査し、2026-09-26 に見送り**

**別方式の検証: ollaya(判定専用モデルのローカル実行基盤) — 現時点では不成立(2026-09-27。ソース調査のみ、実測なし)**:

https://github.com/ollaya-dev/ollaya (Apache-2.0、Rust、2026-09-23 公開)。「Ollama が LLM を動かすように判定モデルをローカルで動かす」デーモン + CLI で、`laya` / `decider` / `kev` / `nli` / `gliclass` / `jevk5` / `winnow` などを名前で pull して `POST /v1/systemone`(TypeSafe 互換)・`POST /api/decide` で提供する。上記「代替候補: Laya」の**実行系の問題を解決している**ため再評価した(Jev 本体は不採用のまま。ollaya は TypeSafe とは無関係の独立プロジェクト)。

- **解決される点**:
  - ローカル実行・API キー不要・重みは HF から commit pin + sha256 検証(再ホストしない)。「すべてローカル完結・外部送信なし」方針と衝突しない
  - **Windows / Mac / Linux バイナリがある**ので、laya-mlx の「Apple Silicon + Python 限定」は解消
  - 速度(Laya モデルカード値、Tesla T4): `laya:multilingual` が **1 問 32.8 ms**、10 問バッチ 72.3 ms。`laya:en` は 39.5 / 158.6 ms。RTX 4090 fp16 で 5 問 9.1 ms(multilingual)。見送り理由 2(Qwen3.5-4B で 1.6 秒 / 件)を桁で潰せる水準
  - サイズ: `laya:multilingual` は重み 614 MB(fp16 safetensors)+ ONNX グラフ 3 MB。Qwen3.5-4B Q4(2.5 GB)より軽い。CPU では fp32 に広げて動かす
  - reranker 不採用の原理的理由(検索関連度 ≠ 述語の充足)には当たらない。Laya は「state + 型付き質問 → 確率」が設計そのもので、`noul`(yes/no)が曖昧 NG の形に一致する
- **設計上の収穫(ollaya を使わなくても効く)**: Laya は**1 回の forward pass で複数の質問に答える**ので、「政治の話題で他人を罵倒している」を「政治の話題か」「罵倒しているか」に分解して AND を取る UI にできる。SemIf 方式・reranker の両検証で唯一かつ共通の誤りが「複合条件の片側だけで反応する」ケースだったので、見送り理由 1(偽陽性)への直接の回答になり得る。**この分解は既存の `score_options` 案(質問 2 本を別々に判定して AND)でも実装できる**
- **不成立の理由 1: 日本語 × 自由記述ルールが空白のマスに落ちる**(最大の問題。Laya モデルカードの Limitations に明記):
  - 日本語が使えるのは `laya:multilingual`(mmBERT-base 322M、100+ 言語)だが、**base checkpoint は zero-shot の typed decisions で 0.362 = ほぼ偶然**。さらに**温度の再フィットなしで出荷**されており(`laya:en` は ECE 0.081、multilingual は値なし)、閾値 UI が信用できない。見送り理由 2 で問題にした「確率が飽和して閾値が効かない」と同じ穴
  - zero-shot に強いのは `laya:typed-decisions`(0.766、Jev 1.13 の 0.727 より上)だが **English only**(ModernBERT-large 421M)
  - つまり「日本語が読めるモデル」と「ユーザーが書いた任意の質問に答えられるモデル」が別物。N23 は両方を同時に要求する
  - カタログの他モデルも英語前提: `decider` は「English only, per the model card」、`nli` / `gliclass` は DeBERTa-v3-large(英語)。`qwen3guard` は質問が固定(安全性カテゴリ)
  - **補足(0.362 という数字の読み方)**: これは typed-decisions の**全体**スコアで、選択肢の多い `choice` 問題に引っ張られている。ollaya 自身の評価では質問タイプ別に `noul`(yes / no)が一貫して高い — schema-scorer が choice 0.362 / score 0.388 / **noul 0.602**、von が 0.367 / 0.367 / **0.632**、jevk5 が 0.568 / 0.576 / **0.747**、decider-4b が 0.682 / 0.632 / **0.742**。曖昧 NG が要るのは `noul` だけなので「0.362 だから駄目」は言い過ぎで、base laya の noul 単独は未公表。ただし 0.6〜0.75 という水準は、偽陽性を強く嫌う NG の絶対判断には依然として届かない
- **不成立の理由 2: ランタイムが別系統**。Ember は llama.cpp / GGUF、Laya は ONNX Runtime。選択肢は
  - (a) `ort` + `tokenizers` を core-ai に追加し、onnxruntime の共有ライブラリをプラットフォームごとに同梱 → **新規 crate 承認 + 配布物の構成変更**が必要
  - (b) ユーザーに ollaya デーモンを別途インストールさせて `http://localhost:11435` に HTTP → localhost なので外部送信には当たらないが、**見送り理由 5(対象ユーザーが薄い)が決定的に悪化**する(AI 有効 + モデル DL + 別ソフトの導入)
  - ollaya の crate(`ollaya-runner` / `ollaya-decision`)は **crates.io 未公開**。git 依存にすると `ort` / `tokenizers` / `ndarray` / `axum` / `tokio` / `libloading` が付いてくる
- **不成立の理由 3: 既存基盤にそのまま乗る GGUF 勢は逆に重い**。`jevk5`(Qwen3.5-4B Q8_0、4.48 GB、RTX 4090 で 5 問 288 ms、CPU 未計測)、`winnow:e4b`(Gemma 4 E4B Q8_0、8.01 GB、**24 コア CPU で 5.1 秒 / 決定**)、`winnow:12b`(12.67 GB、16 GB GPU が下限)。Qwen3.5-4B Q4 より大きく遅いので見送り理由 2 は変わらない
- **変わらない点**: 見送り理由 1(実スレ規模の偽陽性率が未計測)・3(遅延 NG の UX = 読んでいる最中にレスが消える)・4(インフラ先行の計画順序)は、モデルを差し替えても一切解決しない
- **結論**: 現時点では**不成立**(却下ではない)。Laya の Limitations 自身が「多言語版は zero-shot の型付き判定がほぼ偶然」と言っているので、日本語の自由記述ルールでは動かない可能性が高い。ただし ollaya は Laya の実行系の問題(Apple Silicon 限定・クラウド依存)を全部解いているので、**多言語側が typed-decisions 相当にファインチューンされて出た時点で再検討の筆頭になる**。監視対象: https://huggingface.co/convaiinnovations/laya
- **検証したくなった場合の最小手順(Ember に一切手を入れない)**: ollaya を Windows にインストール(`irm https://ollaya.dev/install.ps1 | iex`)→ `ollaya pull laya:multilingual` → `scripts/probe_ng_llm.rs` の日本語 12 件をそのまま `POST /api/decide` の `noul` で投げ、精度と Windows CPU のレイテンシを測る。0.362 という公称値を 5ch のレスで裏取りする形。**ollaya のインストールはユーザー承認が必要**

**別方式の検証: ゼロショット NLI 分類器 (2 ラベル分類ヘッドつき GGUF) — 実測で成立(2026-09-27。検証プローブ `scripts/probe_nli_ng.rs`、Windows / 32 スレッド CPU)**:

上記 ollaya 調査の副産物。ollaya の `nli` ファミリーのドキュメントに「英語以外は `bge-m3-zeroshot-v2.0` を使え」と書かれていたのを追った。**[N23] の見送り理由 1(偽陽性)と 2(速度と精度の両立)の両方が実測で解消した**ので、再検討条件を差し替える。

- **モデル**: `MoritzLaurer/bge-m3-zeroshot-v2.0`(**MIT**、XLM-RoBERTa-large 568M、多言語 100+、8k ctx、月間 12 万 DL)。`XLMRobertaForSequenceClassification` で `id2label = {0: entailment, 1: not_entailment}` の 2 値。「テキスト(前提)に対して仮説が成り立つか」だけを答える汎用分類器で、**NG ルール = 仮説**にそのまま対応する。[N24] で使った `bge-reranker-v2-m3` と同じバックボーン・同じサイズ
- **既存基盤にそのまま乗る(追加 crate なし)**。GGUF は未公開だが llama.cpp の `conversion/bert.py` が `XLMRobertaForSequenceClassification` に対応しており、`config.json` の `id2label` がそのまま `bert.classifier.output_labels` になる → ロード時に `n_cls_out=2`。llama.cpp 側は RANK プーリングで RoBERTa の分類ヘッド(CLS → `cls` → tanh → `cls_out`)を通し、**qwen3 系以外は softmax を掛けない**ので素の logit 2 本が返る(`llama-graph.cpp` の `LLAMA_POOLING_TYPE_RANK`)。`llama-cpp-2` 0.1.154 の `embeddings_seq_ith()` は RANK のとき `float[n_cls_out]` を返す(`embeddings_out_len()` が `n_cls_out` を見る)ので、Rust 側は 2 値 softmax を自前で取るだけ。変換・ロード・推論すべて一発で通った
- **注意**: `with_n_ubatch()` を `n_batch` と同じ値まで上げること。RANK プーリングは 1 シーケンスを 1 回で encode するので、既定の 512 のままだと長いレスで `n_ubatch >= n_tokens` の assert に落ちる
- **PyTorch 参照とのパリティ**: 同じ 12 件・同じ仮説で F16 GGUF と transformers fp32 の P(entailment) の差は最大 0.006(0.9655 → 0.9662 など)。分類ヘッドまで正しく動いている
- **精度(日本語・`probe_ng_llm.rs` と同一の手書き 12 件、ルール「政治の話題で他人を罵倒している」)**: 仮説の書き方で変わる。「この文章は、政治について他人を罵倒する内容である。」で **12/12**(Q4_K_M / Q8_0 / F16 すべて)、「この書き込みは政治の話題で他人を罵倒している。」で 11/12、英語の仮説を日本語本文に当てると 8〜9/12。**[N23] の SemIf 方式(Qwen3.5-4B / Gemma4-E2B)も [N24] の reranker も間違えた「お前みたいなバカがいるからスレが荒れるんだよ。消えろ」(政治要素のない罵倒)を、P=0.085 で正しく非該当にする** — 複合条件の片側だけで反応する問題がこの方式では出ない
- **確率が飽和しない**: Q4_K_M で P の範囲 0.010〜0.962、F16 で 0.003〜0.976。Gemma4-E2B の 0/1 飽和とは違い、**閾値 UI が意味を持つ**。唯一の誤りは偽陰性(「岸田も石破もどいつもこいつも無能。支持してる連中は頭おかしい」が plain 仮説で 0.42)で、NG としては安全側
- **速度・サイズ(CPU、量子化別。手書き 12 件は 36 tok / 件)**:

  | 量子化 | サイズ | 12 件の精度(about 仮説) | 36 tok | 78 tok | 178 tok | 338 tok | スループット |
  |---|---|---|---|---|---|---|---|
  | Q4_K_M | **418 MiB** | 12/12 | **41.6 ms** | 85 ms | 190 ms | 384 ms | 913 tok/s |
  | Q8_0 | 606 MiB | 12/12 | 53.2 ms | 107 ms | 241 ms | 483 ms | 714 tok/s |
  | F16 | 1.08 GiB | 12/12 | 118 ms | 230 ms | 516 ms | 993 ms | 322 tok/s |

  Q4_K_M の 913 tok/s は [N24] で測った bge 系 568M の CPU 上限(約 930 tok/s)と一致する。モデルロードは 0.5 秒
- **実スレ実測(Q4_K_M、Ember の SQLite キャッシュから取り出した実スレ 2 本 × 1002 レス。`scratchpad/dump_thread.py` で TSV 化 → プローブの `file` モード)**:
  - **61 ms / 件**(実際のレス長。1 スレ 1002 件をルール 1 本で **61 秒**)
  - ルール「政治について他人を罵倒する内容」× 政治スレ(嫌儲のイスラエル・イラン戦争スレ): P≥0.9 が 3.1%、P≥0.8 が 10.1%、P≥0.5 が 26.8%。**上位 25 件の目視では 22〜23 件が真陽性に見えたが、これは緩い読みで、正解ラベルを付けて測り直すと適合率はずっと低い(下記「正解ラベル付き評価」)**
  - **同じルール × 非政治スレ(ソフトウェア板の Ember スレ): P≥0.8 が 0.3%(3 / 1002)、P≥0.5 が 1.2%、92% が P<0.1**。しかもその 3 件は「安倍晋三エクスプローラー」という HN を巡る罵倒や「共産党のキチガイ」で、偽陽性とも言い切れない。**ルールが当てはまらないスレではほぼ発火しない**
  - ルールを変えても機能する: 「アプリの不具合や動作の問題を報告している」→ 上位が実際のエラーログ・不具合報告で埋まる(Ember スレで P≥0.8 が 6.2%)、「他人を煽ったり馬鹿にしている」→ P≥0.8 が 0.3% で中身も妥当。**特定ルール専用のチューニングではなく、自然文ルール一般に効く**
- **[N23] の見送り理由との対応**:
  1. 偽陽性 → **半分だけ解消**。ルールが当てはまらないスレでの誤爆は P≥0.8 で 0.3%(1002 件中 3 件)と小さいが、**同じ話題のスレの中では複合ルール 1 本だと適合率 0.46〜0.60 しかない**。単一述語 2 本の AND にすると 0.81 まで上がる。詳細は下記「正解ラベル付き評価」
  2. CPU で速度と精度が両立しない → Q4_K_M 418 MiB で 61 ms / 件・確率も飽和しない。新着 100 件 × ルール 3 本 = **18 秒**(Qwen3.5-4B は 8 分)→ **解消**。GPU 前提のゲーティングも不要
  3. 遅延 NG の UX → 未解決。ただし 61 ms / 件なら「新着 10〜20 件は描画前に同期判定」が現実的で、日常の自動更新はほぼ同期扱いにできる
  4. 計画がインフラ先行 → 本節の測定が精度検証を先に済ませた形になった
  5. 対象ユーザーが薄い → 418 MiB の追加 DL のみ。生成モデル(2.5 GB)も GPU も不要なので、以前より条件は軽い
- **残る課題**:
  - **GGUF が未公開**。llama.cpp の変換で作れる(F16 → `llama-quantize` で Q4_K_M)が、Ember の `ai-models.json` は URL + sha256 で HF から落とす方式なので、**変換済み GGUF をどこかに置く必要がある**(MIT なので再配布は可。上流に投げるか自分の HF アカウントに置くか)
  - `core-ai` のモデルキャッシュが 1 スロットなので、チャット用モデルと判定用モデルの同居に 2 スロット化が必要([N24] と同じ論点)
  - `ai-models.json` に「分類器」という新しい種別が増える。チャットのモデル選択に出てはいけない
  - 実測は 1 台・2 スレ・ルール 3 本・手書き 12 件まで。**再現率(偽陰性)は未計測**で、上位のみ目視した精度なので、正解ラベルを付けた評価はまだない
  - 仮説文の書き方で 12/12 と 8/12 が分かれる。ユーザーが書く自然文をそのまま仮説にすると精度が落ちる可能性があり、UI 側で「〜である。」の平叙文に整える案内か変換が要る

**正解ラベル付き評価(2026-09-27。上記の実スレ実測に対して層化サンプリング + 手ラベルで適合率・再現率を推定した)**:

上記「上位 25 件を目視」は緩い読みだったので、測り直した。方法: 実スレ 1002 件のスコアを P のバンド(≥0.9 / 0.8-0.9 / 0.5-0.8 / 0.2-0.5 / <0.2)に分け、各バンドから 15〜25 件を無作為抽出(seed 固定)して**計 232 件に手でラベルを付け**、バンドの母数で重み付けして母集団を推定した(Horvitz-Thompson)。スクリプトは `scratchpad/make_eval.py` / `metrics.py` / `compare_rules.py`、スコアは `probe_nli_ng.rs` の `file` モードが吐く `*.scores.tsv`。

- **ラベルは 2 段階**。判定基準の幅そのものが結果を左右するため:
  - **厳格** = 明確な罵倒語(クズ / キチガイ / アホ / ユダ公 / 土人 / 老害 など)が人・集団に向いている、かつ政治の話
  - **緩め** = 政治の話で、敵意・嘲り・「滅ぼせ」の類を含む(罵倒語は無くてもよい)
- **結果(ルール「政治について他人を罵倒する内容」× 政治スレ)**:

  | 方式 | 閾値 | 発火 | 適合率(厳格) | 再現率(厳格) | 適合率(緩め) |
  |---|---|---|---|---|---|
  | 複合ルール 1 本 | 0.9 | 31 (3.1%) | 0.60 | 0.19 | 0.73 |
  | 複合ルール 1 本 | 0.8 | 101 (10.1%) | 0.46 | 0.47 | 0.78 |
  | 複合ルール 1 本 | 0.5 | 269 (26.8%) | 0.24 | 0.64 | 0.60 |
  | **政治 AND 罵倒 (min)** | **0.8** | **32 (3.2%)** | **0.81** | 0.26 | **0.94** |
  | 政治 AND 罵倒 (min) | 0.7 | 48 (4.8%) | 0.73 | 0.36 | 0.91 |
  | 政治 AND 罵倒 (min) | 0.5 | 146 (14.6%) | 0.38 | 0.56 | 0.71 |

  推定該当数は厳格で 99 件(9.9%)、緩めで 304 件(30.3%)。このスレは政治的な罵り合いで埋まっているので、厳格と緩めの差がそのまま「ルール文をどう読むか」の幅になる
- **一番重要な発見: ルールを単一述語に分解して AND を取ると適合率がほぼ倍になる**。**発火件数が同じ**(複合 P≥0.9 の 31 件 vs AND≥0.8 の 32 件)条件で適合率 0.60 → **0.81**(緩めなら 0.73 → 0.94)。[N23] の「複合条件の片側だけで反応する」問題は、モデルを変えても消えず、**ルールの持ち方(UI)で消す**のが正解だった。手書き 12 件では複合 12/12 > 分解 11/12 で分解の効果が見えなかったが、実スレ規模では逆転する
- **ルールが当てはまらないスレでの誤爆は小さい**(非政治スレ・同じルール): P≥0.9 で 2 件、P≥0.8 で 3 件 / 1002 件。うち 1 件は「共産党のキチガイ」「クズ」を含む本物なので、**誤爆は実質 1〜2 件 / 1000 レス(0.1〜0.2%)**
- **別ルールでも同傾向**(「アプリの不具合や動作の問題を報告している」× ソフトウェア板): 厳格(書き手自身が問題を報告している)で P≥0.9 の適合率 0.53、緩め(作者の修正報告・要望・回答も含む)で **1.00**。これも「ルール文の解釈幅」がそのまま数字に出ている
- **再現率は低い**。AND≥0.8 で 0.26、複合 P≥0.8 で 0.47。**「全部消す」道具ではなく「一番ひどいものを畳む」道具**で、UI もそう見せる必要がある
- **評価の限界**: ラベルは 1 人(Claude)が付けたもので、ユーザー本人の NG 感覚とは別。スレ 2 本・ルール 3 本・232 ラベルまで。境界例の判断が数字を大きく動かすので、**採否を決める前にユーザー自身が上位 30 件程度を見て「これを消してほしいか」を確認するのが必須**

**この評価を踏まえた実装方針の変更**:
1. **ルールは「単一述語の AND」を基本形にする**。`NgAiRule` は 1 文ではなく述語の配列(`predicates: string[]`)を持ち、各述語に個別の閾値ではなく 1 つの閾値 + `min()` で合成する。UI も「政治の話題である」「他人を罵倒している」のように 2〜3 個に分けて書かせる(1 個でも動く)
2. **既定閾値は 0.8、既定モードは「非表示」**(あぼーんにはしない)。適合率 0.81 は 1000 レスあたり 6 件を誤って隠す水準なので、復元可能でなければ出せない
3. **判定コストは述語の数だけ増える**(61 ms × 述語数)。2 述語で 122 ms / 件、新着 100 件 = 12 秒
4. **「NG にする」より先に「候補を一覧する」UI を出す**。再現率 0.26 なので自動 NG 単独では期待に応えられない。「このスレの該当候補 N 件」を確率つきで並べ、そこから既存の文字列 NG に手で追加できる形が、実測の性能に一番合っている

**実装計画(2026-09-27。ユーザー承認: 上位 30 件の一覧を見て「この精度で消えるのは許容できる」)**:

運用点は**述語 2 本の AND、閾値 0.8、モードは非表示(復元可)**。実測は適合率 0.81(厳格) / 0.94(緩め)、再現率 0.26、発火 2.8%、61 ms / 件 / 述語。**あぼーんを既定にしない・連鎖に乗せない・GPU 前提にしない**の 3 点は動かさない。

- NG パネルに「AI ルール」タブ。`desktop.ngAiRules.v1` → `NgAiRule = { id, predicates: string[], mode: NgMode, threshold: number, disabled?: boolean, addedAt: number }`。述語は 1〜3 個、合成は `min()`
- 「このスレを判定」ボタン → 該当候補を確率つきで一覧。行クリックでそのレスへジャンプ、そこから既存の文字列 NG へ手で追加できる
- 判定モデル未導入 / AI 未有効ならタブを出さない(既存のゲーティングに従う)
- `scripts/smoke_ui_playwright.mjs` に `desktop.ngAiRules.v1` をシードしてタブ・ルール行・閾値 UI を検証するアサーションを追加(判定自体は Tauri 必須なので静的 HTML では走らせない)
- **受け入れ**: 実スレで候補一覧が出て、smoke green。**ここで実際に使ってもらう**

**実装メモ(2026-09-27)**:
- GGUF は https://huggingface.co/votepurchase/bge-m3-zeroshot-v2.0-GGUF に公開済み。`ai-models.json` の判定器エントリ (`kind: "classifier"`) はこの URL・418373760 バイト・sha256 `5d41a1d3…` を指す。変換は `scripts/convert_nli_model.sh` で再現できる
- `classify_entailment()` は計画の単発版ではなく**レス × 述語のバッチ版**にした。コンテキスト生成はペア採点より高くつくので、1 回の呼び出しで 1 コンテキストを共有する
- 判定キャッシュのキーは (スレ URL, レス番号, ルール ID) で、`predicates_hash` 列が一致した行だけ読む。述語を書き換えると古い判定は自動的にヒットしなくなる
- 生成 (要約 / 翻訳 / 返信) と判定は core-ai の同じミューテックスを取り合うので、判定中に生成が来たら `ai_run_inference` の先頭で判定を中断させ、判定側は生成中なら `Err("busy")` で即返す。キャンセルスロットは 2 本に分けた
- 判定器が入っているかは `ai_ng_classifier_ready` で確認し、結果を `desktop.ngAiReady.v1` に残す。起動直後にタブが出たり消えたりしないためと、スモークテストから出し分けを検証できるようにするため
- **M3 の残り**: 実スレで「このスレを判定」を押して候補一覧が出ることの確認。モデルの DL とアプリ実行が必要なのでユーザー側での確認になる

**M4: 自動 NG(M3 の確認後に着手)**
- `aiNgMap`(スレ単位)を `ngResultMap` の 0 パス目としてマージ。既存の 1〜3 パス目は変更しない。**連鎖(ID 連鎖・連鎖あぼーん)には乗せない**
- 新着レスのみ判定。20 件以下は描画前に同期(2 述語 × 20 件 = 約 2.4 秒)、それ超はバックグラウンドで順次
- スレを開いた直後の全件判定はしない(1002 件 × 2 述語 = 約 2 分)。キャッシュヒットのみ即反映
- 「AI ルールで N 件を非表示」の表示と、ワンクリックで全解除できる導線(再現率 0.26 なので「消えすぎ」より「消えない」不満が出る想定)
- **受け入れ**: 新着が裏で判定され閾値以上が非表示になる。ローカル完結で外部送信なし。モデル未有効時は UI に出ない。smoke green

**やらないこと**: あぼーんを既定にする / 連鎖に乗せる / GPU 必須にする / `App.tsx` を分割する / 判定を起動時に走らせる。

**残るリスク**: 再現率 0.26 は「一番ひどいものだけ畳む」水準で、期待値の説明を UI で間違えると「効いていない」と受け取られる。述語の書き方で精度が動く(平叙文が強い)ので、UI に例文を置く。ラベルは 1 人ぶんなので、M3 で実利用の感触を取る。

**対象ファイル(想定)**: `apps/desktop/src/App.tsx`(NG パネル・`ngResultMap`)、`apps/desktop/src-tauri/src/lib.rs`(判定コマンド)、`crates/core-ai/src/lib.rs`(yes/no 判定 API と logit 取得)、`crates/core-store/src/lib.rs`(判定キャッシュ)、`apps/desktop/scripts/smoke_ui_playwright.mjs`

**完了条件(採用した場合)**: ルール追加 → 新着レスが裏で判定され、閾値以上のレスが指定モードで NG になる。判定はローカル完結で外部送信なし。モデル未有効時は UI に出ない。smoke green。

### [N24] スレ内 AI 検索(意味検索・レス並べ替え) — ステータス: ⏸ 見送り(2026-09-26。再検討条件は本節末尾)

**背景**: [N23] のクロスエンコーダ検証で、NG 判定(絶対判断)には使えないが**話題の順位付けには効く**ことが分かった(トピッククエリで ROC-AUC 0.917、30 ms / 件)。その副産物として「相対順位を使う機能なら成立するのではないか」を調査した。現状の Ember のレス検索は `App.tsx` の `toLowerCase().includes()` による部分一致のみで、語が違うと拾えない。

**想定していた機能**: スレ内の意味検索(語が違っても同じ話題のレスを拾う)、関連レス抽出(このレスに似たレスを集める)、話題クラスタ / 脱線レスの提示。

**アーキテクチャは 2 つしかない(2026-09-26 整理)**:

| | クロスエンコーダ (reranker) | バイエンコーダ (embedding) |
|---|---|---|
| 計算単位 | **(クエリ, レス) のペアごと**に 1 forward | レスごとに 1 回だけ、結果を保存 |
| 検索 1 回 | 1000 レス = 1000 forward | クエリ 1 forward + 内積 1000 回(< 1 ms) |
| 事前処理 | 不要 | スレ単位のインデックス作成が必要 |
| 保存 | 不要 | 1024 次元 × 4 B = 4 KB / レス(f16 で 2 KB) |
| 精度 | 高い | 低い |

**実測(2026-09-26。Windows / 32 スレッド CPU、Radeon RX 550。検証プローブは `scripts/probe_rerank_ng.rs` と同じ構成で、埋め込み側はスクラッチのみ)**:

- **バッチしてもスループットが伸びない**。1 decode に複数シーケンスを詰めて k=1 / 4 / 16 / 64 で比較したが、bge 系 568M は **約 930 tok/s で頭打ち**(short 11 tok: k=1 737 → k=64 920 tok/s、med 33 tok: 913 → 850、long 84 tok: 926 → 634 でむしろ劣化)。演算律速でオーバーヘッド削減の余地がない。**GPU(RX 550)は k=64 で 552 tok/s と CPU より遅く**、[N23] の「この GPU は逆に遅い」がそのまま再現した
- モデル比較:

| モデル | サイズ (Q4_K_M) | ms / 件 | 1000 レス | トピック AUC「政治の話題」 |
|---|---|---|---|---|
| `bge-reranker-v2-m3` (568M) | 438 MB | 30 | 30 秒 | **0.917** |
| `jina-reranker-v2-base-multilingual` (278M) | 212 MB | **11** | **11 秒** | 0.750 |
| `bge-m3` 埋め込み (568M) | 417 MB | 36(初回のみ) | 索引 36〜55 秒 → 以後 < 1 ms | top-1 は 4 問中 3 問 |

- **小型化は効かない**。`jina-reranker-v2-base-multilingual` は速度 2.7 倍だが、「ゲームの話題」で AUC 0.875、「食べ物の話題」で 0.667 — どちらも**政治のレスを上位に出す逆向きの誤り**(bge は 0.375 / 0.146 で正しい向き)。日本語のトピック判別が実用水準にない
- **バイエンコーダ(`gpustack/bge-m3-GGUF` Q4_K_M、`bert.pooling_type=2`(CLS)、n_embd 1024)の意味検索は微妙**。「クーラーが壊れた話」→ エアコン / 冷房を top2 で正解、「課金とガチャの不満」も top2 正解。しかし**「政治への文句」で「岸田も石破もどいつもこいつも無能」が top4 にすら入らない**。さらに特定のレス(検証では「エアコン…」)が**全クエリの top4 に居座る**(hubness)。スコアは 0.37〜0.67 に圧縮され、無関係 0.52〜0.58 / 正解 0.65〜0.67 とマージンが薄く、**ここでも絶対閾値は立たず top-k 順位でしか使えない**
- **小型多言語埋め込みの GGUF は信用できない**(再調査時の注意): `multilingual-e5-small` のコミュニティ変換は `tokenizer.ggml.model = bert`(WordPiece)が SentencePiece 語彙(250,037 トークン、`▁` 接頭辞)に付いており、「エアコンの効きが悪くなってきた」が ` for|効| for|悪| for` の 5 トークンに壊れる(`keisuke-miyako` / `milimyname` 版で確認)。別の変換(`cstr` 版)は `tokenizer.ggml.token_type_count` 欠落で `bert model needs to define token type count` となりロードすら失敗する。`gpustack` の変換は `bge-m3` / `bge-reranker-v2-m3` ともに正常だが、同社は小型多言語埋め込みを出していない

**機能案と成立条件**:

1. **クロスエンコーダ + 明示操作**(インデックス不要・SQLite 変更なし・ストレージ増加ゼロ・鮮度問題なし): ボタン / Enter で発火して全レスをスコアリングし上位順に並べる。**1000 レスで 30 秒**は専ブラの検索として遅すぎるが、対象を「表示中の範囲」「直近 200 レス」に絞れば **6 秒**で実用圏。進捗バーとキャンセルが必須
2. **バイエンコーダ索引 + 即時検索**: スレを開いた裏で 36〜55 秒かけて索引を作れば以後の検索は一瞬。ただし新レスの差分索引、`thread_cache` とは別テーブル、f16 でも 2 MB / スレ(本文 JSON の 4〜5 倍)、そして**精度が案 1 より明確に落ちる**
3. **ハイブリッド**(索引で top-50 → リランカーで並べ替え): 精度は最良だが**モデル 2 本で 855 MB** になり非現実的

**統合コスト(案 1 の場合)**: `core-ai` に `rerank_scores(model_path, query, docs, backend, cancel) -> Vec<f32>` を追加(`complete_streaming` のモデルキャッシュ機構を流用可)。ただし **`MODEL_CACHE` は 1 スロットなので、リランカーを載せるとチャットモデルが落ちる** — 検索のたびに数 GB の載せ替えが起きるため 2 スロット化が必要。`ai-models.json` にリランカー枠(`recommendedFor: ["rerank"]`)。`App.tsx`(13,893 行)に検索モード切替と進捗 UI。

**見送り判定(2026-09-26)**:

1. **速度と精度が両立しない**。精度が要求水準に届くのは 568M クラスだけで、それは CPU で 930 tok/s = 1000 レス 30 秒。小型化すると日本語のトピック判別が逆向きに壊れる。GPU 前提にする案は [N23] と同じゲーティング問題を抱え、しかも手元の RX 550 では CPU より遅い
2. **検索専用にもう 1 本モデル(212〜438 MB)を落とさせる**話になる。[N23] の見送り理由 5「対象ユーザーが薄い」がそのまま当てはまり、今回はさらに条件が厳しい
3. **既存の部分一致検索がそこそこ強い**。5ch のレスは同じ単語が使われやすく、置き換えではなく上積みにしかならない
4. バイエンコーダ案は精度・ストレージ・鮮度の 3 つで同時に妥協を要求され、割に合わない

**再検討する場合の条件(この順で)**:

1. まず案 1 を「対象は直近 200 レス、`core-ai` に関数 1 本 + 既存のレス検索欄にモード追加」だけの試作にする(SQLite・索引・バックグラウンド処理は作らない)
2. 実スレ 5〜10 本で、**部分一致検索と比べて実際にどれだけ違う結果が出るか**を数える。「部分一致で拾えたものしか出てこない」なら却下に落として理由を記録する
3. 信用できる小型多言語埋め込み / リランカーの GGUF が出たら 1 の対象範囲を広げられる。判断基準はトピッククエリの AUC 0.9 以上(上表の `bge-reranker-v2-m3` 相当)

**対象ファイル(想定)**: `crates/core-ai/src/lib.rs`(`rerank_scores` とモデルキャッシュの 2 スロット化)、`apps/desktop/src-tauri/src/lib.rs`(検索コマンド)、`apps/desktop/src/App.tsx`(レス検索欄のモード切替・進捗 UI)、`apps/desktop/src-tauri/ai-models.json`、`apps/desktop/scripts/smoke_ui_playwright.mjs`

**完了条件(採用した場合)**: レス検索欄で AI 検索モードに切り替えると、対象範囲のレスが関連度順に並ぶ。キャンセル可能で進捗が見える。ローカル完結で外部送信なし。モデル未有効時は UI に出ない。smoke green。
